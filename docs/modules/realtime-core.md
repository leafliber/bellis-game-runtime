# 实时核

Rust 写的独立进程，是游戏侧的安全核：采集画面与声音，并作为唯一的输入代理，在本地强制执行许可、白名单与释放（GD-01、GD-02）。它不是插件，不热替换，只在没有输入许可时更换。G0 实现启动、采集与假输入后端，G1 加音频，G2 接真实输入。

## 职责

- 按窗口采集游戏客户区，写入帧环；按进程采集游戏的声音，写入音频环。
- 按动作块执行输入，每次输入前在本地核对[权威规则](../architecture.md#权威)中的三个条件。
- 强制执行游戏适配包的动作白名单与静态禁区。
- 维护持键账目，任何失效时释放全部输入并核验。
- 检测真人接管与其他程序的注入，监听本地急停热键。

## 不负责

- **决策。** 动作由主进程的控制产出者决定。
- **识别画面。** 按画面类型的规则（危险画面、风险等级）只在主进程执行，见[动作风险](step-control.md#动作风险)；实时核不识别画面，这是剩余风险。
- **签发许可。** 许可来自 Bellis 的控制连接（[游戏桥](game-bridge.md#连接)）或独立运行的操作员入口（G2，形式另行登记批准）；G0 只有只用于测试的测试许可源（[输入许可](core-protocol.md#输入许可)）。

## 启动与生命线

| 游戏是否提权 | 实时核的启动 |
| --- | --- |
| 不提权 | 主进程以 `subprocess.Popen` 拉起非提权子进程，停止顺序为 RPC → 关 stdin → 超时强制终止，Windows 上用 Job Object 管住孙进程（Bellis R-06），见下文。G0 实现 |
| 提权 | 维护者一次性注册的计划任务（GR-06），见下文。G2 或原神阶段实现 |

两种启动之后的生命线、控制状态与释放相同。主进程一侧的代码在 `runtime/src/game_runtime/core_link/`，实时核一侧在 `core/crates/realtime-core`。

### 非提权子进程

主进程的 `CoreLink` 每次 `start` 都拉起一个新的实时核实例，与 Bellis `startSidecar` 的做法相同：

1. 以 `session_credentials` 生成本实例的会话地址与密钥，在 `bellis-channel/1` 上开服务端监听。每个实例的凭据都是新的，被杀或已退出的旧实例连不上。
2. 以 `subprocess.Popen` 和参数列表拉起 `realtime-core`：不经 shell，不用 `DETACHED_PROCESS`、`CREATE_BREAKAWAY_FROM_JOB` 或 `start_new_session`；stdin 是管道，stdout 与 stderr 继承主进程。
3. 环境变量按 Bellis 的 `baseEnvironment` 只取系统必需的（Windows 的 `SYSTEMROOT`、`PATH` 等，POSIX 的 `HOME`、`PATH` 等），其余不继承；凭据按 Bellis 的 `ChildEnv` 放在 `BELLIS_CHANNEL_PATH`（地址）、`BELLIS_CHANNEL_KEY`（base64url 密钥）与 `BELLIS_ROLE`（角色，固定为 `game-runtime.core`）里。时限经命令行参数 `--heartbeat-timeout-ms`、`--health-interval-ms`、`--max-frame-age-ms` 给出。只用于测试：`CoreLinkOptions.test_device` 给出时另加 `--input-backend fake`，测试设备的地址与密钥放在 `GAME_RUNTIME_TEST_DEVICE_PATH`、`GAME_RUNTIME_TEST_DEVICE_KEY` 里（[测试设备连接](core-protocol.md#测试设备连接)）。
4. Windows 上以 `CREATE_SUSPENDED` 创建，放进 Job Object 并交出 job 句柄之后才恢复运行，见下文。
5. 实时核连上后发 `core.hello`；主进程只接受角色为 `game-runtime.core` 的第一个连接，核对协议版本，不相等即以 -32001 回错并断开。收到 `input.released(core_start)` 才算就绪。从拉起到就绪超过 `start_timeout` 或实例在就绪前退出，即按停止顺序终止它并报 `CoreStartError`。
6. 配置了采集（`CoreLinkOptions.capture`）时先挂接帧环、再设定采集目标，被拒绝即按停止顺序终止它并报 `CoreStartError`（[帧环的挂接](core-protocol.md#读写规则)）。之后开始发心跳。

实例退出后宿主可以再 `start`，即重启。自动重启按 GR-35，G2 接真实输入之前实现，现在 unsupported：

- 实例非 0 退出（panic 的 101、被强杀、运行中失败）后，`CoreLink` 按 1、2、4 秒退避重新拉起，至多 3 次，每次上报宿主；就绪后连续运行满 60 秒，次数清零。
- 重启的实例照常先释放全部输入（`core_start`）再接受动作；等待中的 `wait_released` 由它的 `core_start` 完成（[释放](#释放)）。
- 不重启：主进程要求的停止、按生命线退出（退出码 0）、参数不合法（2）。次数用尽即停止并上报，由操作员处理。
- 被杀的实例留下的按键只能靠新实例尽快启动后结束，见[失效与释放](../architecture.md#失效与释放)中的“实时核崩溃”。

### Job Object

job 设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`：最后一个 job 句柄关闭时，系统终止 job 里剩下的进程。这样做既能管住孙进程，又不会在主进程崩溃时立即杀掉实时核：

- **先进 job 再运行。** 实时核以 `CREATE_SUSPENDED` 创建，主进程把它放进 job、交出句柄后，在线程快照里找到它唯一的初始线程恢复运行。它在进 job 之前做不了任何事，拉起的孙进程也一定在 job 里。`subprocess.Popen` 不保留线程句柄，所以按进程号找线程。
- **job 句柄交给实时核一份。** 主进程以 `DuplicateHandle` 把 job 句柄复制进实时核（只有 `JOB_OBJECT_QUERY` 权限，不可继承）。实时核不知道也不使用这个句柄，只是持有它到退出。主进程崩溃时系统关闭主进程的句柄，但实时核持有的那份让 job 不关闭；实时核按生命线释放全部输入后退出，最后一个句柄随之关闭，job 终止残留的孙进程。被杀的实时核发不出按键抬起，所以“主进程崩溃”时实时核是唯一的释放者，不能随主进程一起被杀。
- **强制终止整个 job。** 停止顺序的最后一步以 `TerminateJobObject` 终止实时核连同孙进程。实时核自行退出后，job 里若还有进程（孙进程），主进程终止它们再关闭自己的句柄。

实测（Windows 11）：
- 不复制句柄时，主进程关闭它的 job 句柄的一刻实时核即被终止；复制之后实时核照常运行，主进程被杀后按生命线释放并以 0 退出。由 `test_link.py` 的主进程被杀测试核对。
- 因 `KILL_ON_JOB_CLOSE` 被终止的进程退出码为 0，与正常退出无法区分。主进程在实时核运行期间始终持有自己的句柄，所以它观察到的实时核不会以这种方式结束。
- 以 `uv run` 或虚拟环境的 `python.exe` 运行的主进程自己在启动器的 job 里，这个 job 设了 `KILL_ON_JOB_CLOSE` 与 `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`：主进程拉起的进程静默脱离它，启动器退出不会连带杀掉实时核。主进程的启动方式不得把实时核放进会随主进程退出而关闭、又不允许脱离的 job。

其它平台没有 Job Object，不收拾孙进程（unsupported）；实时核本身不拉起子进程。

### 停止

主进程的停止顺序：先停插件内核，控制产出者走完 [QUIESCING](plugin-kernel.md#控制产出者)；再按 Bellis R-06 停实时核（`shutdown_runtime`）。每一步的时限可配置（`StopTimeouts`），实时核在哪一步退出记日志：

| 步 | 做法 | 缺省时限 | 实时核 |
| --- | --- | --- | --- |
| 1. RPC | `core.stop` | 2 秒，从发出请求到退出 | 释放全部输入，发 `input.released(stop)`，回应写出后以 0 退出 |
| 2. 关 stdin | 关闭 stdin 管道 | 2 秒 | 读到 EOF，释放后以 0 退出 |
| 3. 强制终止 | Windows 上 `TerminateJobObject`，其它平台 `SIGKILL` | 5 秒，只作上报的界限 | 被终止，不释放 |

第 1、2 步的时限取 Bellis `ManagedProcess` 的缺省值；实时核的释放与回应在毫秒内完成，2 秒是给卡住的实时核留的余量。请求失败（连接已断、超时、对端报错）不影响后续步骤。实时核退出后 `stop` 销毁帧环；强制终止后仍未确认退出时保留。

### 生命线与 panic

实时核在以下任一情形释放全部输入后退出，原因写进 stderr 的日志：

| 情形 | 通知主进程 | 退出码 |
| --- | --- | --- |
| 收到 `core.stop` | `input.released(stop)`，回应写出后才退出 | 0 |
| 核连接断开 | 无法通知（原因 `core_connection_lost` 只记日志） | 0 |
| stdin 读到 EOF 或读取失败（主进程要求停止或已退出） | `input.released(stdin_closed)`，连接还在时发出，至多等 200 ms 写出，随即退出 | 0 |

- 断开与 EOF 都由阻塞读立即发现，不需要计时；主进程卡死而连接未断时由心跳超时释放并待命，不退出。
- 以假后端运行时，退出前至多等 500 ms 把释放全部输入的抬起与 `release_all` 写给测试设备；主进程崩溃时测试一方由此看到释放（[测试设备连接](core-protocol.md#测试设备连接)）。
- 退出码 0 只在释放之后出现；连不上主进程或测试设备、握手失败为 1，参数不合法（含测试许可源的门禁）为 2。
- **panic 即退出。** 标准库在非主线程 panic 时只结束那个线程，读线程或调度线程的 panic 会被吞掉。实时核启动时装 panic 钩子：照常打印 panic 信息后以 101 退出整个进程。钩子里不释放输入，panic 时的状态不可信；重启后先释放（`core_start`）。
- **提权时**（计划任务启动）没有 stdin 管道，stdin 生命线须能关闭：unsupported，随 GR-06 实现。

### 控制状态与心跳

规则见[消息集](core-protocol.md#消息集)中的“控制产出者”；这里只写实现，时刻读的时钟见[时钟](#时钟)：

- 实时核记当前产出者（身份、代次、上一个算数的 `seq`、心跳截止时刻、上一个接受的动作块序号与这一代次已执行过的动作身份）、已作废的最高代次、输入许可、调度计划与持有输入的账目，放在一把锁里（`control.rs`）。时刻一律是 `mono_clock::now_ns()` 的读数。
- 心跳由主进程的 `CoreLink` 发：当前提交资格（`kernel.active_control`）有效时每个周期发一次，身份取 `ControlGrant.producer`（条目 id），代次取 `ControlGrant.generation`，`seq` 在主进程运行期间全局递增，因而在每个代次内严格递增。资格收回（进入 QUIESCING）即停发。一个代次的第一块动作之前另发一次，见[提交动作块](plugin-kernel.md#提交动作块)。
- 调度线程等到心跳截止时刻即释放（`heartbeat_timeout`）并待命：产出者仍是当前的，同一代次 `seq` 递增的心跳到达后重新计时。
- **启动的顺序。** 每次启动先释放全部输入，再连接主进程；握手完成、`input.released(core_start)` 发出之后才启动处理产出者消息的读线程与发送线程，所以 `core_start` 一定先于任何因产出者消息而发的通知。以假后端运行时，测试设备连接在释放之前就连上，测试设备因而也收到 `release_all(core_start)`。
- 实时核每次启动都没有当前产出者与已作废的代次；代次由主进程的插件内核分配，在主进程运行期间单调递增，所以也满足“在一个实时核的生命期内严格递增”。

主进程以 `core.health` 判断实时核存活：`CoreLink` 记下最近一条与收到的时刻，超过 `health_timeout` 没有新的即记录告警；实时核退出或连接断开另有进程退出与连接关闭的事件。

### 释放

释放是唯一的安全路径。持有输入的账目与“释放全部输入”是实时核内部的一个接口（`InputLedger::release_all`）：任何失效都在控制状态的锁内调用它，它按与按下相反的顺序对每个按住的项调用输入后端的抬起，再告诉后端已全部释放，然后清空账目；释放完成后才读释放时刻、才在锁外发 `input.released`。释放不依赖核连接、帧环写入或采集线程：输入后端在锁内只把事件放进队列，从不等网络写入（[输入后端](#输入后端)）；写失败也已经释放。账目、假后端与真实后端的分工见[持键账目与释放](#持键账目与释放)。

`CoreControl` 的实现（`CoreLink`）：`invalidate_generation` 发 `producer.revoke` 并在请求写出后返回；`wait_released` 按以下任一事件完成，等待跨实例保留：

- `producer.revoke` 的回应：该代次及更早代次的输入已释放；
- 新实例的 `input.released(core_start)`：此前的等待全部完成；
- 实例以 0 退出：实时核只在释放后以 0 退出；此后没有实例在运行时，新的等待也立即完成。

实例被强制终止或崩溃（退出码非 0）时没有进程发出按键抬起，等待保留到下一个实例的 `core_start`，插件内核在此期间保持 QUIESCING（`release-timeout`）。

### 线程

实时核用标准线程加阻塞 IO，不用异步运行时：

| 线程 | 做什么 |
| --- | --- |
| 主线程 | 以假后端运行时先连上测试设备；释放、连接、握手、发 `core_start`，启动其余线程，然后等会话结束 |
| `RpcPeer` 读线程 | `producer.heartbeat`、`producer.revoke`、`core.stop`、`action.submit`、`frame_ring.attach`、`capture.set_target` 的处理函数：只动控制状态、发通知或把命令交给采集线程，很快返回，不向主进程发请求。`action.submit` 只校验并装进调度计划，不执行任何一步 |
| 调度 | 按时刻执行动作块的步，负责全部定时的释放：心跳超时、许可到期、持有输入时帧龄超限、截止时刻，见[动作块的执行](#动作块的执行) |
| 核连接的发送 | 写出调度线程与测试设备连接的线程放进队列的通知（回执、`input.released`） |
| 健康 | 握手后立即发一次 `core.health`，之后按周期发 |
| 采集 | 取帧写进帧环，见[采集主循环](#采集主循环) |
| 两条生命线 | 一个等核连接关闭，一个读 stdin 直到 EOF |
| 测试设备连接（只在假后端时） | 读线程处理 `test_lease.grant`、`test_lease.revoke`；发送线程写出假输入事件；一条生命线等它断开，断开即许可失效 |

通知有两条出口：读线程上的处理函数直接写（`producer.revoke` 与 `core.stop` 由此在回应之前发出 `input.released`）；调度线程与测试设备连接的线程放进发送队列，由发送线程写，它们因此从不等网络写入，主进程卡住时只有发送线程阻塞。两条出口之间的先后不定。`core.stop` 以 `Handlers::request_then` 登记（见[错误处理](core-protocol.md#错误处理)）：回应写出之后才通知主线程结束会话，否则退出会丢掉回应。日志写 stderr，写失败丢弃，不 panic。

### 时限

| 项 | 缺省值 | 在哪里配置 | 依据 |
| --- | --- | --- | --- |
| 心跳周期 | 100 ms | `CoreLinkOptions.heartbeat_interval` | 主进程的事件循环被 GC 或同步代码占住几十毫秒不算异常；Windows 的计时精度约 15.6 ms |
| 心跳超时 | 500 ms | `CoreLinkOptions.heartbeat_timeout`，经命令行交给实时核 | 连续丢失约 5 次才超时；主进程卡死后输入最多多保持约 0.5 秒，动作块自己的截止时刻通常更短；误判只会多一次释放 |
| `core.health` 周期 | 1 秒 | `CoreLinkOptions.health_interval`，经命令行交给实时核 | 只用于诊断与判断卡死；实时核退出由进程退出与连接关闭立即发现 |
| `core.health` 超时 | 3 秒 | `CoreLinkOptions.health_timeout` | 连续丢失 3 条 |
| 动作允许的帧龄 | 500 ms | `CoreLinkOptions.max_frame_age`，经命令行交给实时核 | 30 Hz 时约 15 帧没有更新，与心跳超时同一量级；不进动作块，产出者不能放宽它 |
| 测试许可的有效期与续约间隔 | 500 ms、250 ms | `FakeDevice.renew`（只用于测试） | 取 Bellis D-34 的游戏输入许可初值与续约间隔 |
| `action.submit` 的请求 | 2 秒 | `CoreLinkOptions.rpc_timeout` | 处理函数只校验，毫秒内回应 |
| 退出前写完通知与假输入事件 | 200 ms、500 ms | 实时核内的常量 | 输入此前已经释放，等不到也照常退出 |
| 启动 | 10 秒 | `CoreLinkOptions.start_timeout` | 含连接的握手（2 秒）与 `core.hello`（2 秒）；新编译的程序首次运行可能被杀毒软件扫描几秒 |
| `producer.revoke` 的请求 | 2 秒 | `CoreLinkOptions.rpc_timeout` | 超时只记录，等待由其它事件完成；内核另有 `release_timeout` |
| `core.hello` 的回应 | 2 秒 | 实时核内的常量 | 与通道握手的缺省时限相同 |
| 停止各步 | 2、2、5 秒 | `CoreLinkOptions.stop` | 见上文“停止” |

这些取值只在测试与假后端上跑过；真实输入下的表现（误判的频率、主进程卡死到释放的时延）在 G2 实测，PENDING。

### 提权时的计划任务（GR-06）

- 任务“以最高权限运行”：只按需启动、无触发器、交互令牌，重复启动时忽略新实例。
- 参照 Bellis R-26，以 `subprocess.Popen`（参数列表，不经 shell）调 `schtasks.exe /Create /XML` 注册；任务 XML 由代码生成，注册后以 `/Query /XML` 读回核对。注册由维护者本人执行。
- 主进程先把本次的连接信息写入 SecretStore，再以 `schtasks /Run` 触发；实时核自行读取主进程与 Bellis 的连接信息（Bellis R-23）。
- 正常停止经 RPC，`schtasks /End` 只作最后手段。
- 实时核程序与配置放在只有管理员能写的目录（由一次提权的安装步骤放入），防止主进程内的代码替换后借任务提权。这道防护只防程序与配置被替换；威胁模型同 Bellis D-12，不防同一用户下的恶意进程：它可以触发任务、写 SecretStore 并连上实时核，但没有 Bellis 经控制连接发给实时核的输入许可就发不出任何输入，独立运行的测试许可只在测试中使用。
- [GS-03](../plan/spikes.md) 实测可行（2026-10-31，用代替实时核的探针）：非提权进程 `schtasks /Run` 触发的任务以 High 完整性级别运行，读到同一用户的 SecretStore 条目，连上非提权主进程建的管道、通过认证并写入帧环；非提权进程改写、重命名、删除管理员目录中的程序，或在其中新建文件，都被拒绝。其他本机用户拿不到数据：维护者决定不测（2026-10-31）；远程客户端被拒由通道测试覆盖。

## 画面采集

用 Windows Graphics Capture 按窗口采集（GR-07），直接基于 `windows` crate 实现，`windows-capture` 等现成 crate 只作参考、不作依赖。代码在 `core/crates/capture`，WGC 部分用 `cfg` 隔离，只在 Windows 上编译。帧环由主进程创建，布局见[核协议](core-protocol.md#帧环与音频环)。真机结论见[实测](#实测)。

- 只采认定的窗口，找不到即没有帧；不采整屏，不采鼠标指针。
- 实时核声明为按显示器感知 DPI v2，坐标一律用物理像素。
- 游戏须为窗口化或无边框全屏，不支持独占全屏。
- GPU 降采样：unsupported（G0 不需要）。需要时先在 GPU 上缩小再读回，不在 CPU 上缩放。

### 采集源接口

采集源实现 `CaptureSource::next_frame(timeout, &mut Frame)`：等到下一帧，写进调用方给的 `Frame` 并复用其像素缓冲；超时内没有新帧时返回“无新帧”，`Frame` 不变。每次交出最新的一帧，其间到达的旧帧丢弃。WGC 采集源与供自动测试用的假采集源实现同一接口。

| 每帧 | 内容 |
| --- | --- |
| 像素 | BGRA8，只含客户区，自上而下逐行 |
| 宽、高、行跨度 | 客户区的物理像素尺寸；行跨度为宽 × 4 字节 |
| 帧号 | 从 1 开始，采集源取到的每一帧都占一个号，被丢弃的也占；相邻两次交出的帧号之差减一即其间丢弃的帧数 |
| 采集时刻 | QPC 纳秒，见[时钟](#时钟) |
| 变换版本 | 见[客户区与变换版本](#客户区与变换版本) |
| 客户区原点 | 客户区左上角在屏幕上的物理像素坐标 |
| DPI | 客户区所在显示器的有效 DPI，96 为 100% 缩放 |

### 管线与线程

1. 识别窗口，建 D3D11 硬件设备（BGRA 支持），经 `CreateDirect3D11DeviceFromDXGIDevice` 得到 WinRT 设备。
2. `IGraphicsCaptureItemInterop::CreateForWindow` → `Direct3D11CaptureFramePool::CreateFreeThreaded`（BGRA8，2 个缓冲）→ 会话；关闭鼠标指针采集，处理[黄色采集边框](#黄色采集边框)，开始采集。
3. 帧池在系统线程上触发 `FrameArrived`，回调只记数并唤醒等待者；采集项的 `Closed` 回调只置标志。
4. 其余都在调用 `next_frame` 的线程上：取出帧池里积压的帧，只留最新的一帧；立即查询窗口几何并算出客户区裁剪框；`CopySubresourceRegion` 复制到同尺寸的 staging 纹理 → `Map` → 逐行复制进 `Frame` → `Unmap` → 关闭 WGC 帧。D3D11 立即上下文只在这一个线程上使用，采集源在哪个线程创建就在哪个线程使用。
5. 帧的画面尺寸与帧池不同（窗口改变了尺寸）时按新尺寸重建帧池；画面比帧池纹理大的帧被截断，丢弃。
6. 等帧期间每 100 ms 检查一次窗口状态，没有帧时关闭、最小化与独占全屏也能及时报出。

会话的最小帧间隔（`MinUpdateInterval`）可配置，缺省用系统值；实测 Windows 11 上缺省读回 16 ms，帧率因此不超过约 60。

实测 WGC 只在窗口内容变化时出帧：内容静止的窗口在开始采集后不再出帧，帧龄一直增长；只移动窗口而不重画，通常也不出帧。窗口重画了相同的内容也算变化：合成游戏的外壳按 30 Hz 重画静止的画面时，WGC 持续出帧（[窗口外壳](offline-tools.md#窗口外壳)）。《魔女审判》停在静止的对话画面时仍持续重画，WGC 约 60 fps 出帧（[实测](#实测)），所以[失效与释放](../architecture.md#失效与释放)中按帧龄判定“采集冻结”不受影响，权威规则不改。不重画静止画面的游戏会因帧龄超限而不执行动作，接入时按 GS-01 的方法实测。

### 采集主循环

实时核怎样把采集源接到帧环上，代码在 `core/crates/realtime-core/src/frames.rs`。主进程一侧的挂接顺序与单写方规则见[读写规则](core-protocol.md#读写规则)。

- **处理函数**：`frame_ring.attach` 与 `capture.set_target` 在 `RpcPeer` 的读线程上核对参数。前者以 `FrameRingWriter::attach` 打开并核对帧环；后者核对窗口识别规则与平台是否支持，假显示面在这里先打开一次。核对通过就把写入方或目标作为命令交给采集线程，随即回应；错误码见 [`capture.set_target`](core-protocol.md#消息集)。
- **采集线程**独占写入方与采集源，帧环在实时核里只有这一个写方。WGC 采集源不是 `Send`，目标以“建立采集源的方法”交给采集线程，采集源在采集线程上创建与使用，继承进程的 DPI 声明；WGC 采集源用缺省配置：请求去掉[黄色采集边框](#黄色采集边框)，最小帧间隔用系统值。
- **一轮**：等命令，至多等到下一轮；没有采集源时按目标建立；`next_frame` 至多等 50 ms，命令因此至多等这么久才处理；取到帧就写进帧环，记下它在帧环中的帧号与采集时刻。
- **挂接与设定目标**的先后不限，两者都到了才建立采集源。再次设定目标时先停掉旧的采集源，再按新目标立即建立，不等重新识别的间隔。再次挂接换成新的帧环，最近写入的一帧随之清空。
- **写不进帧环的帧**（比帧环的最大尺寸大等）丢弃，帧环不受影响，最近写入的一帧不变。
- 状态变化写 stderr 的日志；同样的问题（找不到窗口、写不进帧环等）只记一次，恢复出帧时再记一次。

| 状态（`core.health.capture`） | 含义 |
| --- | --- |
| `idle` | 还没有挂接帧环或设定采集目标 |
| `searching` | 有帧环与目标，没有采集源：找不到窗口，或采集源已失效，正在定期重新识别 |
| `capturing` | 有采集源；可恢复的情形下暂时没有新帧 |

| 从 | 事件 | 到 | 之后 |
| --- | --- | --- | --- |
| `idle` | 帧环与目标都到了，建立采集源成功 | `capturing` | 取帧 |
| `idle` | 同上，建立失败：`WindowNotFound`、`AmbiguousWindow` 等 | `searching` | 每 500 ms 重新识别 |
| `searching` | 重新识别并建立成功 | `capturing` | 取帧 |
| `capturing` | 可恢复的错误：`WindowMinimized`、`ExclusiveFullscreen` | `capturing` | 保留采集源，每 100 ms 再取帧；没有新帧，帧龄增长 |
| `capturing` | 不可恢复的错误：`WindowClosed`、`Os`、假采集源的 `InvalidFrame` 等 | `searching` | 丢掉采集源，500 ms 后重新识别 |
| `searching`、`capturing` | 再次设定目标 | 建立成功为 `capturing`，否则 `searching` | 旧的采集源先停掉 |
| 任何 | 会话结束 | — | 停掉采集源，至多等 500 ms；等不到也照常退出 |

这些间隔是 `frames.rs` 里的常量，只在测试与真机测试中跑过，未按真实游戏调整。

**帧龄的依据。** 采集线程每写进一帧，就把它在帧环中的帧号、采集时刻与客户区几何（尺寸与 DPI）记进 `FrameStatus`；控制状态持有它，`core.health` 的 `latest_frame` 也报它。[权威规则](../architecture.md#权威)的“帧未超过动作允许的年龄”据它判断（[动作块的执行](#动作块的执行)）：没有新帧时（采集冻结、最小化、窗口关闭、写不进帧环）它不前进，帧龄随之增长。它只记本实例写的帧：新实例写出第一帧之前为 `null`，帧环里旧实例写的帧不算，这期间帧龄按超限处理。几何的变化点供[坐标与几何](core-protocol.md#坐标与几何)的核对；再次挂接帧环时与最近一帧一起清空。

**释放与采集解耦。** `FrameStatus` 有自己的锁，最近一帧的采集时刻另存一份原子量。采集线程只在更新它的一瞬间持锁，取帧与写帧时不持锁，也从不碰控制状态的锁；[释放](#释放)只用控制状态的锁，帧龄的检查（权威检查与持有输入时的定时检查）只读原子量，所以采集线程卡在 WGC 里或写帧失败都不影响释放。几何的查询拿 `FrameStatus` 的锁，锁序是先控制状态、后 `FrameStatus`。

### 时钟

实时核与主进程读同一个单调时钟，核协议中以 `_ns` 结尾的时刻、帧环的采集时刻与 `core.health.now_ns` 都是它的纳秒读数。主进程读 `time.perf_counter_ns()`；实时核读 `mono-clock` crate 的 `now_ns()`，不用 `std::time::Instant`：

| 平台 | `perf_counter_ns` | `now_ns` |
| --- | --- | --- |
| Windows | QPC 刻度按 `刻度 × 10⁹ / 频率` 向下取整 | 同一换算（`qpc_ticks_to_ns`） |
| Linux | `CLOCK_MONOTONIC`（Python 3.12） | `clock_gettime(CLOCK_MONOTONIC)` |
| 其它 | 别的时钟（macOS 上是 `mach_absolute_time`） | 不支持，编译即报错 |

两边读同一时钟由测试实测核对，Windows（命名管道）与 Linux 容器（UDS）上都通过：实时核收到握手回应之后才发第一条 `core.health`，它的 `now_ns` 落在主进程回应之前与收到它之间；`producer.revoke` 的释放时刻落在主进程发请求前与收到回应后的两次读数之间。

采集时刻取 WGC 帧的 `SystemRelativeTime`。它是 QPC 换算成的 100 ns 单位，采集时刻 = `SystemRelativeTime × 100` 纳秒。

- **换算误差。** QPC 频率为 10 MHz（Windows 10 起常见）时，100 ns 单位就是 QPC 刻度，两边相等，误差为 0。其它频率下两边各自取整，误差的绝对值不超过 100 ns。
- **采集时刻的含义。** 实测采集时刻可能晚于帧交给调用方的时刻几毫秒，推测是 DWM 合成的目标显示时刻（PENDING 核实）。所以“现在 − 采集时刻”可能为负，用帧龄的地方把负值按 0 处理。

### 客户区与变换版本

几何在取到帧之后立即查询，都是物理像素；调用线程须为按显示器感知 DPI v2，否则报错。

| 量 | 取法 |
| --- | --- |
| 窗口边界 | `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，即 WGC 窗口画面覆盖的屏幕范围，不含不可见的缩放边框与阴影 |
| 客户区原点 | `ClientToScreen` 换算客户区的两个角，取左上的一个（从右到左布局的窗口也成立） |
| 客户区尺寸 | `GetClientRect`。系统把不感知 DPI 的窗口的客户区尺寸按缩放比换算成物理像素交给 v2 线程；不用 `ClientToScreen` 换算右下角，因为它先取整到逻辑像素，175% 缩放下实测少 2 个像素 |
| DPI | `MonitorFromWindow` 与 `GetDpiForMonitor(MDT_EFFECTIVE_DPI)` |

**裁剪。** 画面尺寸须等于窗口边界的尺寸，否则这帧与当前几何不是同一时刻（窗口正在改变尺寸），丢弃。客户区在画面中的偏移 = 客户区原点 − 窗口边界原点；客户区须完全落在窗口边界内且不为空，否则丢弃。丢弃的帧分类计数，探测程序报告。

**变换版本。** 变换是客户区原点、客户区尺寸与 DPI 三者。变换版本从 1 开始，交出的帧的变换与上一次交出的不同即加一，所以窗口移动、缩放或 DPI 变化时加一；只有窗口边界变化而客户区不变时不加。同一版本的帧可以共用坐标换算。版本在交出帧时才更新：窗口变化后到下一帧之前，帧环中的最新帧仍是旧版本，而只移动窗口通常不出帧，这段时间可能一直持续，所以输入路径注入前另行核对窗口。

**边缘。**
- Windows 11 给有边框的窗口画圆角：客户区底部两角半径约 8 个逻辑像素以内的像素被裁成半透明（alpha < 255），WGC 如实采到。无边框窗口不受影响。
- 不感知 DPI 的窗口由系统拉伸显示，边缘与物理像素不对齐，有不到 1 个像素的模糊。

### 窗口识别

- 按识别条件匹配可见、未隐藏（cloaked）的顶层窗口：进程映像文件名（不含目录，不区分大小写）、窗口类名（精确）、标题（精确），给出的条件须全部满足。游戏的条件为进程名加窗口类或标题；G0 由配置给出，G1 起来自游戏适配包。
- 空条件不匹配任何窗口。没有符合的窗口即没有帧；多于一个时报错，不猜测。
- 进程映像路径以 `PROCESS_QUERY_LIMITED_INFORMATION` 查询，这一权限可以跨完整性级别打开进程；提权游戏的识别没有实测，维护者决定 GS-01 不测提权的游戏窗口（2026-10-31）。
- 只在建立采集源时识别一次；窗口关闭后须重新识别并新建采集源，由[采集主循环](#采集主循环)完成。

### 不支持的情形与报错

不支持的情形一律明确报错，不静默地没有帧。建立采集源时与采集期间都检查。

| 情形 | 错误 | 之后 |
| --- | --- | --- |
| 找不到窗口 | `WindowNotFound` | 重新识别 |
| 不止一个窗口符合 | `AmbiguousWindow` | 收紧识别条件 |
| 窗口已关闭 | `WindowClosed` | 重新识别并新建采集源 |
| 最小化 | `WindowMinimized` | 可恢复，还原后继续出帧 |
| 独占全屏 | `ExclusiveFullscreen` | 可恢复，切回窗口化或无边框全屏后继续 |
| 调用线程不是按显示器感知 DPI v2 | `NotPerMonitorDpiAwareV2` | 修正进程的声明 |
| 系统不支持 WGC | `Unsupported` | — |
| 系统调用失败 | `Os` | 新建采集源 |
| 假显示面里的槽头部不合帧环布局（只有[假采集源](#假采集源)会报） | `InvalidFrame` | 修正测试一侧的写入 |

独占全屏的判断：`SHQueryUserNotificationState` 报告 Direct3D 独占全屏，且前台窗口属于目标窗口的进程（独占全屏只在程序处于前台时成立）。真机验证 PENDING。窗口被其它窗口遮挡不影响采集，客户区完整。

### 黄色采集边框

先以 `GraphicsCaptureAccess::RequestAccessAsync(Borderless)` 请求访问，再把会话设为 `IsBorderRequired = false`。两步的结果与读回值都记录并由探测程序报告，失败不阻止采集。API 读回的值不等于屏幕上看不到边框，所以真机测试截取屏幕上窗口边界附近的像素对照：保留边框时出现黄色像素，请求去掉后没有。实测 Windows 11 上未打包的程序请求结果为 `Allowed`，边框去掉，《魔女审判》上截屏核对同样如此；与 OBS 同时采集时 OBS 画面里的表现 PENDING，提权游戏不测。

### 实测

GS-01，2026-10-31，Windows 11 Pro 10.0.26200，单屏 3840×2160、缩放 175%，《魔女审判》窗口化（客户区 2560×1440）。原始输出在不入库的 `reports/gs01/`。

| 情形 | 结果 |
| --- | --- |
| 停在静止的对话画面 30 秒 | 59.8 fps，没有超时与丢帧，帧交出时帧龄不超过 6 ms |
| 拖住标题栏移动窗口 | 拖动期间照常出帧（57–60 fps），每到一个新位置变换版本加一 |
| 其它窗口挡住一部分、焦点切走 | 帧率不变 |
| 最小化与还原 | 最小化时报 `WindowMinimized`、不出帧；还原后马上继续出帧，变换版本不变 |
| 黄色采集边框 | 保留时屏幕上可见，请求去掉后不可见 |
| OBS 同时采集同一窗口 | 实时核一侧 22 秒内每秒 58–61 帧，帧龄不超过 8 ms，与不开 OBS 时相同；OBS 一侧的帧率、丢帧与画面没有记录（PENDING） |
| 经 `CoreLink` 与实时核进入帧环（帧环 3840×2160） | 约 58 fps，帧尺寸 2560×1440；主进程首次读到时帧龄中位约 25 ms、最大约 48 ms，含 Python 读出整帧的拷贝 |

- 这款游戏的窗口不能拖边改变尺寸，尺寸只能在游戏设置里改，所以没测改变尺寸。
- 无边框模式、DPI 缩放与提权的游戏窗口：维护者决定不测（2026-10-31）。
- 缺省的帧环最大尺寸（1920×1080，见 `CaptureConfig`）装不下这个客户区，帧会写不进去（[采集主循环](#采集主循环)），所以实测时把帧环设为 3840×2160。

### 假采集源

只用于自动测试：在没有窗口与 WGC 的环境里（含 Linux 容器）跑除采集与注入外的全链路（[合成游戏](offline-tools.md#合成游戏)的自动测试）。生产中不使用。代码是 `core/crates/frame-ring` 的 `FakeCapture`，实现同一[采集源接口](#采集源接口)。

- **假显示面**：一块与[帧环](core-protocol.md#帧环)同一布局的共享内存，代替游戏窗口。测试一侧（Python）创建、写入与销毁它，写法与实时核写帧环相同（`game_runtime.frame_ring.fake.FakeDisplay`，只用于测试）：把 `SyntheticGame.frame()` 逐帧写进去，相当于游戏把画面显示出来；采集时刻缺省取写入时的 `time.perf_counter_ns()`，与真实采集同一时钟。复用帧环的布局，不另定格式：Python 一方的创建与 Rust 一方的打开、核对都与帧环共用。
- **目标**：`capture.set_target` 的 `fake` 分支，`surface` 是假显示面的共享内存名与布局参数，打开与核对的规则同 `frame_ring.attach`（[创建、命名与销毁](core-protocol.md#创建命名与销毁)）。
- **取帧**：每 1 ms 查看一次假显示面的 `write_seq`，有比上次交出的更新的帧就按[读写规则](core-protocol.md#读写规则)读最新的一帧，读到撕裂就等下一轮；超时内没有新帧即返回“无新帧”，帧不变。帧号、采集时刻、变换版本、宽高与行跨度取自假显示面，其间没交出的帧算作丢弃；没有窗口，客户区原点为 (0, 0)，DPI 为 96。
- **报错**：假显示面的槽头部在 seqlock 下稳定却不合布局时报 `InvalidFrame`，不可恢复。
- 假采集源只能证明链路通，不验证 WGC、窗口识别、几何与时钟；真机验收仍走 WGC（Bellis D-11）。

用 WASAPI 进程回环按游戏进程 ID（含子进程）只采游戏的声音（GR-08），PCM 带 QPC 时间戳写入音频环，与帧环同一时钟；音频环由主进程创建。不用端点回环与虚拟声卡。配音忙闲由主进程判断，见[感知](perception.md#配音检测)。

## 输入代理

### 输入后端

实时核把输入交给输入后端（`ledger.rs` 的 `InputBackend`）：按下（键、鼠标键，或把轴设为某个取值）、抬起、一次性动作（点击、短按、滚动、相对位移）与“释放全部已完成”。每个方法都在控制状态的锁内调用，须很快返回，不能等网络写入；按下类只在权威检查通过之后调用，抬起类随时可以调用。

| 后端 | `--input-backend` | 状态 |
| --- | --- | --- |
| 没有后端 | 不给 | G0 生产中的配置：动作块照常校验与调度，但没有许可源，权威检查从不通过，不发任何输入（`no_lease`） |
| 假输入后端，只用于测试 | `fake` | G0 实现，见下文 |
| 真实后端（SendInput） | 无 | unsupported，G2 实现；给出其它取值以参数不合法（2）退出 |

### 假输入后端与测试设备连接

只用于测试（`fake.rs`），协议与门禁见[测试设备连接](core-protocol.md#测试设备连接)：

- 假后端把每个按下、抬起、一次性动作与释放全部作为 `fake_input.event` 放进发送队列就返回，由测试设备连接的发送线程写给测试一方。测试一方（`FakeDevice`）独立记下“当前按住了什么”，可以把事件转给合成游戏的状态机（[合成游戏](offline-tools.md#合成游戏)）。
- 同一条连接上的测试许可源授予、续约与吊销许可；连接断开即没有许可（`lease_source_lost`）。测试许可源只在假后端的代码里构造：`InputSetup::select` 只在 `--input-backend fake` 与测试设备的凭据同时给出时才选出它，二者缺一即以 2 退出（`config.rs`）；没有后端时许可没有来源。
- 假后端上测得的时序（定时精度、释放时延）不代表真实输入，真实输入在 G2 实测。

### 注入

用 SendInput 注入（GR-09）：键盘发扫描码；点击把客户区物理像素换算为绝对坐标后移动、按下、按住、抬起，按住时长写在游戏适配包；每个注入事件的 `dwExtraInfo` 带本次会话的标记。不用窗口消息、虚拟 HID 或内核过滤驱动。G2 实现，现在 unsupported。

每次注入前核对：游戏窗口在前台，落点在客户区内，窗口未最小化且不在安全桌面，以及[权威规则](../architecture.md#权威)的三个条件（G0 已在假后端之前核对，见[动作块的执行](#动作块的执行)）。注入后再核对一次前台，焦点中途变化即报部分提交或结果未知，不自动重试。从不自动把游戏切回前台，失焦时上报并暂停输入。

### 白名单与静态禁区

游戏适配包写明允许的扫描码、鼠标键、点击区域、最高动作速率与最长按住时间，以及不论画面都不能点的静态禁区（GR-21）。实时核在白名单之外强制执行静态禁区，不满足即拒绝该动作并上报。

### 持键账目与释放

持键账目（`InputLedger`）按按下的顺序记录本实例按下且尚未抬起的每一项：键按扫描码、鼠标键按键、轴按轴名（取值改变时原地更新）。任何失效都按[失效与释放](../architecture.md#失效与释放)释放全部输入：按相反的顺序逐项抬起，告诉后端已全部释放，再清空账目，见[释放](#释放)。

- 假后端上，抬起与 `release_all` 是交给测试一方的事件，测试一方据此核对释放是否完整。
- 真实后端上释放后以 `GetAsyncKeyState` 核验：G2，unsupported。
- 被杀的实例发不出抬起；新实例的账目是空的，它的 `core_start` 释放不知道旧实例按住了什么。假后端上由测试实测为残余风险（[失效与释放](../architecture.md#失效与释放)的“实时核崩溃”）；真实后端上新实例能否据 `GetAsyncKeyState` 补发抬起在 G2 定，PENDING。

### 接管与急停

- 低层键鼠钩子在专用线程上运行，回调只入队。
- 没有“已注入”标志的真人动作（鼠标位移超过阈值才算）与不带本会话标记的注入都按接管处理：本地撤权、释放全部输入、上报。Bellis 切到人工模式，交还控制只能由操作员执行。
- 实时核同时监听 OBS 急停热键（Bellis R-27）的组合键，按下即释放全部输入并上报，不依赖 Bellis 转发；组合键在配置中与 OBS 的绑定保持一致。
- 反作弊拦截或标记注入的输入时按合规停止信号处理，不绕过。

待实测项见 [GS-02](../plan/spikes.md)。

## 动作块的执行

动作块的形式与规则见[核协议](core-protocol.md#动作块)，这里写实现（`control.rs`）。实时核按时间戳执行，到有效截止时刻还没有新的动作块就释放；只接受当前控制产出者与当前代次的动作块。即时游戏需要的定时精度由 [GS-08](../plan/spikes.md) 实测。

**接受。** `action.submit` 的处理函数在读线程上先处理到现在为止到期的一切（与调度线程同一段代码），再按 `stopping`、产出者、内容、序号、截止时刻的顺序校验；被拒绝的块不改变任何状态。接受时更高的代次先释放再切换（`producer_changed`），然后把块装进调度计划：上一块起始时刻之后未执行的步回执 `superseded`，必要时在上一块的截止时刻插入一步空的持续状态。处理函数不执行任何一步，回执与释放的通知放进发送队列。

**调度线程。** 一个线程在一把锁下维护调度计划，按单调时钟醒来，每轮依次处理：

1. 心跳截止时刻已到：释放（`heartbeat_timeout`）并待命。
2. 许可到期时刻已到：释放（`lease_expired`）。
3. 持有输入且最新写入帧的帧龄超过上限：释放（`frame_stale`）。持续状态因此不只在发新动作时检查。
4. 时刻已到的步：逐步执行，见下文。所属的块已过截止时刻的步不再执行（醒得晚了的旧块只做抬起，动作回执 `superseded`）。
5. 在效块的截止时刻已到：释放（`deadline_expired`），这一块结束。

下一次醒来的时刻取心跳截止、许可到期、下一步、在效块的截止时刻，以及持有输入时帧龄超限的时刻中最早的一个；状态改变（心跳、新块、许可、作废）时被唤醒重算。Windows 上条件变量的等待按毫秒取整，系统计时精度约 15.6 ms，醒来可能晚到这么多；GS-08 实测。

**执行一步与权威检查。** 每次把一个输入交给后端之前，都核对[权威规则](../architecture.md#权威)的三个条件：许可有效（[输入许可](core-protocol.md#输入许可)）；当前控制产出者是这一块的产出者，且心跳截止时刻未到；本实例最新写入帧的帧龄（现在减采集时刻，负值按 0）不超过动作允许的帧龄（`--max-frame-age-ms`，缺省 500 ms，不进动作块）。一步之内：

1. 抬起账目里不在这一步持续状态中的项：抬起是安全方向，不检查。
2. 按下这一步持续状态里尚未按住（或轴取值不同）的项：每项之前检查。
3. 按列出的顺序执行一次性动作：本代次已执行过的身份回执 `duplicate`；带坐标的动作在基准帧之后几何变了的回执 `geometry_changed`（[坐标与几何](core-protocol.md#坐标与几何)）；其余每个之前检查，通过即交给后端，回执 `executed`。

检查不成立即不发，在同一把锁内释放全部输入与持续状态（原因取第一个不成立的条件），这一块随之结束：其余动作回执 `released`，之后的步不再执行。每执行完一步，这一步的动作回执一次。

**线程安全。** 释放路径不依赖采集线程、帧环写入或网络写入：帧龄读 `FrameStatus` 的原子量；后端只把事件放进队列；通知在锁外放进发送队列或由处理函数直接写，写失败也已释放。读线程上的处理函数只做内存里的校验与状态变化，很快返回。
