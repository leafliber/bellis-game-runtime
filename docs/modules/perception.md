# 感知

主进程中读懂画面与声音的普通插件：OCR、画面状态（变化、签名与类型）、配音检测、界面元素检测。它们只产出数据与候选，没有权威；读出的文字是不可信数据（见[权威](../architecture.md#权威)）。VLM 见[模型接入](models.md)。G1 实现 OCR、画面变化与签名、配音检测；G2 把 `scene@1` 扩展为画面状态服务；界面元素检测在第二款游戏接入时实现。

## 职责

- 识别游戏适配包给出的区域里的文字及其位置。
- 判断画面是否稳定、命中了哪个签名、属于哪种画面类型，并给出来源与置信度。
- 判断游戏配音正在播放、已结束或未知。
- 找出画面上可点击的界面元素。

## 不负责

- **决定动作。** 由[逐步控制](step-control.md)决定。
- **判断一句对白是否完整。** 逐字显示时的完整判断属于[剧情记录](narrative-planner.md#剧情记录)。
- **训练模型。** 不用任何游戏截图训练或微调（[合规](../compliance.md)）。

## 取帧

读画面的插件都经帧源取帧，代码在 `runtime/src/game_runtime/frames/`。帧源由宿主构造内核时交给内核，清单申请了 `frames.read` 的插件从 `ctx.frames` 取得（[注册](plugin-kernel.md#注册)）；实时运行的定序帧源、测试用的内存帧源与录制的回放帧源都是这个接口的实现。G1 实现。

- **帧**：沿用帧环的 `RingFrame`：像素（BGRA8，自上而下逐行）、宽、高、行跨度、帧号、采集时刻（与 `time.perf_counter_ns()` 同一时钟）与变换版本。
- **接口**：`FrameSource.next_frame(after)` 等到帧号大于 `after` 的一帧并返回；帧源结束（关闭后读完、回放读完）后返回 None。帧源不记读者的进度，每个读者自己记下读到的帧号。
- **被处理的帧**：每个帧源给出一个确定的帧序列，每个读者都按顺序逐帧读到，不跳过。插件的结果只取决于依次处理的帧，时刻一律取帧的采集时刻，不读墙钟；同时用到画面与声音的结果按采集时刻对齐，不按到达的先后（[配音检测](#配音检测)）。实时运行时读者处理的就是定序帧源接纳的序列，录制写下同一序列，回放按录制的顺序给出同样的帧，所以得到逐帧相同的结果。
- **内存帧源** `MemoryFrameSource` 供测试：`push` 依次放入帧号递增的帧；`close` 之后读完即结束。
- **回放帧源** `ReplayFrameSource` 按录制的顺序逐帧解码给出，读完即结束，见 [M0 回放](offline-tools.md#m0-回放)。
- **线程**：拷帧、解码与重计算放在工作线程，不阻塞事件循环；被取消时等在途的工作做完再交出取消，插件停用时不会留下还在读帧环的线程。

### 定序帧源

`SequencedFrameSource` 读主进程的帧环，决定接纳哪些帧，接纳的每一帧按顺序交给每个读者。帧环在它关闭之前不关闭：主进程先关闭它、停插件内核，再停实时核。

**接纳。** 泵任务每隔 `poll_interval`（缺省 20 毫秒）看一次最新帧号；距上次读帧至少 1/`max_rate` 秒（墙钟）且有新帧时，在工作线程里按[读写规则](core-protocol.md#读写规则)拷出最新一帧，与上一接纳帧比较：

| 情形 | 接纳 |
| --- | --- |
| 第一帧，或尺寸、变换版本、像素与上一接纳帧有任何不同 | 接纳 |
| 都相同 | 采集时刻距上一接纳帧不短于 `idle_interval` 才接纳；像素与上一接纳帧共用同一个对象 |

- `max_rate` 缺省每秒 10 帧，读帧与接纳都不超过它。对白逐字显示时每秒有多帧变化，接纳间隔就是读帧间隔；两次读帧之间到达的帧不读、不接纳。
- 内容不变时仍定期接纳，让按采集时刻计算的稳定时长前进：`idle_interval` 缺省 0.25 秒，与 `scene@1` 的 `stable_after` 相同，稳定的判定因此至多晚一个读帧间隔。帧环没有新帧（窗口不重画）时不接纳，不凭空造帧。
- 每次尝试都读到撕裂的帧时下一轮再读。
- `poll_interval` 不短于 Windows 上事件循环的时钟精度（约 15.6 ms）：更短的定时器一排上就算到期，几个这样定时的任务互相唤醒，事件循环不再休眠、空转占满一个核（录制时实测：录声音的任务按 10 ms 定时，主进程从约 23% 升到约 110% 的单核）。

**积压。** 接纳的帧放在有界的队列里，至多 `backlog` 帧（缺省 32，2560×1440 时约 470 MB；与上一帧像素相同的帧共用对象，不另占内存），满了移出最旧的。读者要的下一帧已被移出（`after` 小于被移出的最大帧号）即积压超限：`next_frame` 抛 `FrameBacklogError`，带上可以继续的位置 `resume_after`（被移出的最大帧号），帧源计数并记告警。读者从 `resume_after` 继续，即从队列里最旧的一帧接着读，跳过的帧不再给它；此后它的结果与回放不一致，录制的元数据记下超限的次数。接纳开始很久之后才开始读的读者同样超限。

**接收方。** 宿主可以给一个接收方（`sink`，即录制的写入方）：泵把接纳的帧交给读者之后，等接收方收下才读下一帧。接收方忙时泵不读帧环，也就不接纳新帧，接纳帧率随之降下来；录制因此不缺任何接纳过的帧，降下来的帧率在录制工具的状态行里看得到。接收方抛错即停止接纳，帧源按关闭处理，错误由 `failure` 给出。

**关闭。** `close` 让泵做完手头的一帧后停下，不取消它；读者读完队列里的帧后得到 None。`wait_ended(n)` 等到读到结束的次数达到 n，宿主以此等全部读者处理完已接纳的帧。`stats` 给出接纳的帧数、读帧的次数、最新的帧环帧号与积压超限的次数。

## OCR

普通插件 `ocr`（GR-10）提供 `ocr@1`，依赖 `game-adapter@1`，不申请权限：它只识别调用方交来的帧，自己不取帧，所以不申请 `frames.read`。代码在 `runtime/src/game_runtime/ocr/`。

- PP-OCRv5 系列模型经 ONNX Runtime 运行；不引入 PaddlePaddle 框架本身，前后处理用 RapidOCR 一类的现成封装或自写，随 GS-04 确定。
- 只识别游戏适配包给出的 ROI（如名字栏、对白框、选项、审判发言区）或调用方给出的矩形，不扫整帧。
- 服务另提供签名的固定文字项所用的 `read_lines`，见[固定文字的 OCR 接口](#固定文字的-ocr-接口)。
- 先在 CPU 上运行，GPU 执行器为可选项。
- 识别语言按游戏适配包声明（《魔女审判》为简体中文）。
- 具体版本与许可在 GS-04 后确定，模型文件作为制品管理（[模型制品](game-adapter.md#模型制品)）。Windows 自带 OCR 作为 GS-04 的对照基线。

### 接口

| 方法 | 输入 | 失败 |
| --- | --- | --- |
| `recognize(frame, roi)` | 帧与适配包里的 ROI 名；归一化矩形按这一帧的宽高换算为物理像素（[坐标](game-adapter.md#声明文件)） | 没有声明即 `LookupError`；尚未标定即 `NotCalibratedError`，不回退到其它区域，也不猜坐标（[尚未标定](game-adapter.md#尚未标定)） |
| `recognize_rect(frame, rect)` | 帧与客户区物理像素的矩形，含左边与上边、不含右边与下边 | 为空或超出帧即 `ValueError` |
| `check_language(frame, screen)` | 画面 `screen` 的稳定帧 | 见下文[语言核对的执行](#语言核对的执行) |
| `check_script(text)` | 一段文字；不做 OCR | 见下文[语言核对的执行](#语言核对的执行) |
| `read_lines(frame, rect)` | 同 `recognize_rect`，只返回各行文字；同步，见[固定文字的 OCR 接口](#固定文字的-ocr-接口) | 同 `recognize_rect`；服务已停用即 `OcrClosedError` |

前三项是协程；`check_script` 是同步的纯计算，可以在事件循环里调用；`read_lines` 是同步方法，在调用方的线程里阻塞到识别做完，不能在事件循环里调用。做 OCR 的四项都交给同一个工作线程，见下文[线程与时延](#线程与时延)。`OcrService` 满足 `scene@1` 的 `TextReader`（[固定文字的 OCR 接口](#固定文字的-ocr-接口)）：同一个 `ocr@1`，`scene@1` 只以这一项取用。

- **帧**：BGRA8，自上而下逐行，带宽、高、行跨度、帧号与变换版本，即帧环读出的 `RingFrame`；接口只要求这几项（`FrameLike`），录制回放的帧满足它即可。识别期间帧的像素不能改变。
- **输出** `OcrResult`：帧号、变换版本、ROI 名（按矩形识别时为空）、识别的区域，以及从上到下、从左到右排列的行。每行是文字、识别框（客户区物理像素，含左边与上边、不含右边与下边）与识别置信度（[0, 1]）；置信度低于配置 `min_confidence`（缺省 0.5）的行丢弃。识别框直接作为[定位与吸附](step-control.md#定位与吸附)的目标。
- **固定文字的比较**：语言核对与画面签名的固定文字项都按[语言核对](game-adapter.md#语言核对)的规则（`RoiText.matches`）比较。
- 读出的文字是不可信数据（见上文）。

### 线程与时延

- 识别在 `ocr@1` 自己的一个工作线程里按调用的先后串行进行，事件循环只等结果；ONNX Runtime 推理时释放 GIL。`read_lines` 可以在多个线程里同时调用，同样排队。排队的时间计入调用的时延，调用方不应堆积请求。
- 调用方被取消时，还没开始的识别不再进行，已开始的照常做完、结果丢弃。停用时不再接受新的识别，等在途的做完，排队的以 `OcrClosedError` 结束。
- 激活时核对与加载模型同样在线程里进行。
- 配置 `threads` 设 ONNX Runtime 的算子内线程数，缺省 4，`null` 由 ONNX Runtime 自定；与游戏同机运行时取多少随 GS-04 定。每次识别的时延按 GS-04 的口径实测，未测前 PENDING。

### 引擎

当前实现是 GS-04 的候选之一：检测与识别两个模型，前后处理自写，只用 numpy 与 OpenCV（`engine.py`）。流程与参数取 PaddleOCR 3.x 通用 OCR 产线的缺省值：

- **检测**：短边不足 64 时放大到 64、长边超过 4000 时缩小（上限随 GS-04 定），宽高取 32 的倍数；DB 后处理取概率大于 0.3 的区域的最小外接矩形，区域内平均概率不低于 0.6 才保留，按面积乘 1.5 除以周长向外扩张。
- **识别**：检测框透视变换为水平的行图，高缩放到 48、宽按比例，每 6 行一批；CTC 贪心解码，置信度为保留下来的字的概率均值。
- 不做文档方向分类、文本行方向分类与扭曲矫正：游戏的文字是正的。

另加两步，配置里可关掉，关掉即 PaddleOCR 原样的后处理；是否保留随 GS-04 定：

- **同行合并**：纵向重叠不少于较矮者一半的水平框算同一行，相邻两框的间隙不超过较高者的高度即合并为一个外接矩形。DB 常把一行在全角标点处断开，或把行末的句号单独检出成小框。
- **识别前加宽**：水平框左右各加宽行高的 1/4 再裁出行图，识别框仍报检测框本身。DB 常漏掉画在字格左下角的行末标点。

模型组有 `ppocrv5-mobile`（缺省）与 `ppocrv5-server`，配置 `model` 选择，缺省随 GS-04 重新确定。

### 模型制品

清单在 `runtime/src/game_runtime/ocr/models.py`，管理规则见[模型制品](game-adapter.md#模型制品)；配置 `data_dir` 是本地数据目录，绝对路径，缺省按[术语](../architecture.md#术语)中的位置与 `BELLIS_GAME_RUNTIME_DATA`。缺省用 mobile 一组（GS-04），server 一组留作对照：

| 制品 | 来源 | 许可 |
| --- | --- | --- |
| 检测与识别模型（mobile、server 各两个 ONNX 文件） | PP-OCRv5 的模型作者 PaddlePaddle 只发布 Paddle 格式的权重，转换要装 PaddlePaddle；ONNX 文件取自 RapidOCR 项目（RapidAI）在魔搭社区的模型仓库 `RapidAI/RapidOCR`，钉在标签 v3.10.0，摘要与 RapidOCR 3.10.0 的 `default_models.yaml` 一致；原始权重为 Hugging Face 上 PaddlePaddle 的 `PP-OCRv5_mobile_det` 等四个仓库 | Apache-2.0（RapidOCR 模型仓库与 PaddlePaddle 的原始权重） |
| 识别字表 `ppocrv5_dict.txt`（18383 字） | 模型作者的 PaddleOCR 仓库标签 v3.0.0 的 `ppocr/utils/dict/`，与 ONNX 文件内嵌的字表逐行相同 | Apache-2.0 |

激活时识别模型的类别数须等于字表的字数加 2（CTC 的空白与空格），不等即激活失败。

### 语言核对的执行

两层都在 `ocr@1` 的服务上，按[语言核对](game-adapter.md#语言核对)：

- `check_script(text)`：文字系统一层。对一段文字（使用方给剧情记录里完整的句子）数属于适配包语言的文字系统的字母比例，给出计数的字母数、其中属于这个文字系统的个数、比例与是否相符；没有可数的字母时比例与是否相符都为空（无从判断）。不做 OCR，同步。纯函数在 `game_runtime.ocr.script`，适配包的语言不在支持的文字系统里时激活失败。
- `check_language(frame, screen)`：固定文字一层。取适配包里画面 `screen` 的各项，逐项识别它的 ROI 并比较，给出每一项的识别结果与是否相符，各项都相符才通过。这个画面没有声明任何一项即 `LookupError`。调用方给出稳定帧与它所在的画面。

两层何时核对、不符时怎样停下并上报由使用方（逐步控制）决定。G1 的只读运行入口在前几句完整的句子上与画面每次出现时核对并报告，见[只读运行的语言核对](offline-tools.md#只读运行的语言核对)。

激活时，适配包的语言版本不在所选模型组核对过的语言里（当前只有 `zh-Hans`，含带地区的如 `zh-Hans-CN`）即激活失败。

### GS-04 的评测工具

离线工具 `tools/gs04-ocr/`（`uv run gs04`），不进运行时。

- **样本**：一个目录，含 `samples.toml` 与它引用的图像。`samples.toml` 可写顶层 `game`（适配包 `id`，ROI 名按它换算）；每个 `[[samples]]` 有 `image`（相对 `samples.toml` 的 PNG，整个客户区）、`category`（类别：对白 `dialogue`、名字 `name`、选项 `choice`、审判发言 `trial`，也可以是其它标识）、`roi`（ROI 名）或 `rect`（物理像素矩形，二者恰好写一个），`text`（真值，多行以换行分隔），以及可选的 `tags`（标签名到取值的表，如 `{ font = "msyh", size = "22" }`，评测另按每个标签分组）。《魔女审判》的样本与真值只存本地数据目录（C-1、C-4、C-5），建议放在 `samples/gs04/<游戏>/` 下。
- **合成样本**：`uv run gs04 synth <目录>` 把两组样本写进同一个 `samples.toml`，真值已知，文字都是原创的，不取任何游戏的台词；`--width`、`--height` 改分辨率（缺省 1280×720）。
  - **合成游戏**：合成游戏的每句台词（显示完的与逐字显示到一半的）、名字、选项提问、选项、坏结局的文字与标题菜单的按钮，ROI 取它的适配包，用来验证工具本身。
  - **泛化**：为评测原创的 20 句对白（含全角标点、数字与拉丁字母），渲染在对白框的位置（客户区宽的 8%–92%、高的 60%–95%，即样本的 `rect`），左上对齐、按字折行，类别为 `general`，逐字显示到一半的为 `general-partial`（按显示完时排好的行截取前一半的字，字的位置不变）。每种字体按字号 × 底色的 20 个组合各渲染一个样本，第 i 个字号、第 j 种底色用第 (i + 2j) mod 3 种字形；每 4 个组合另有一个逐字显示到一半的。各字体所用的对白、字号、底色与字形相同（缺字时除外），按字体分组即可比较字体。每个样本带四个标签：
    - `font`：Windows 自带的中文字体中本机有的微软雅黑 `msyh`、微软雅黑粗体 `msyh-bold`、黑体 `simhei`、宋体 `simsun`、楷体 `simkai`、等线 `dengxian`、仿宋 `simfang`，从 `%WINDIR%\Fonts` 就地读取，不复制、不入库、不下载；一种也没有时（如 Linux 容器）或给了 `--no-system-fonts` 时退回合成游戏的字体子集 `synthetic-sans`。每种字体只用它的字表覆盖得到的句子，不够 20 句时补上合成游戏的台词、选项提问与坏结局的文字，仍不够时轮换。
    - `size`：字号（像素），客户区高 720 时为 16、22、30、42，其它高度等比缩放。
    - `background`：深色纯色 `dark`、浅色纯色 `light`、斜向渐变 `gradient`、噪声纹理 `texture`、纹理与色块上叠半透明深色框 `translucent`。
    - `style`：无修饰 `plain`、深色描边 `outline`、右下阴影 `shadow`。浅色底上无修饰与阴影的字为深色，其余为白色。
- **评测**：`uv run gs04 eval <样本目录>` 对每个样本识别一次，按类别、按每个标签的每个取值（只计入带这个标签的样本）与总计给出字符准确率与时延分布；`--engine` 选 `ppocrv5-mobile`、`ppocrv5-server` 或 `windows`；`--threads`（0 由 ONNX Runtime 自定）、`--det-max-side`（检测输入的长边上限）、`--no-merge`、`--no-pad` 对照引擎的配置。
- **字符准确率**：1 减去编辑距离之和除以真值字数之和，预测与真值都先各行依次连接并去掉空白；另给出两边先做 NFKC 归一（全角与半角标点视为相同）后的值。
- **时延**：每个样本一次识别的墙钟时间（裁出、检测与识别，不含排队），给出 p50、p90、p95、p99、最大与均值；第一次调用含预热，单独记录、不计入分布。
- **Windows 自带 OCR**（`Windows.Media.Ocr`）：只在 Windows 上，是评测工具的可选依赖（`uv run --extra windows-ocr gs04 eval … --engine windows`），系统须装有简体中文的 OCR 语言组件；它直接识别同一区域裁出的图像，不经本仓库的前后处理。
- **报告**写到不入库的 `reports/gs04/`：JSON 与 Markdown 各一份，含日期、系统与 CPU、引擎及其配置、模型制品的摘要、ONNX Runtime 版本、每个样本的预测与真值，以及上面的统计。结论由维护者写回技术基线 GR-10。

### OCR 的依赖

运行时：onnxruntime（MIT），随它装入的 flatbuffers（Apache-2.0）与 protobuf（BSD-3-Clause）；numpy 与 opencv-python-headless 同下文 `scene@1` 的[依赖](#依赖)。评测工具读字体的字表用 fontTools（MIT）；可选依赖 `windows-ocr`：pywinrt 的 `winrt-runtime` 与 `winrt-Windows.*` 各包（MIT），只在 Windows 上安装。版本见 `uv.lock`；模型制品的许可见上文[模型制品](#模型制品)。

## 画面变化与签名

普通插件 `scene@1`（GR-12），分两部分：与游戏无关的变化与稳定检测；按游戏可选的画面签名，只为有快路径的画面写。逐步控制器据前者决定何时动作，VLM 只在画面稳定且相对上次调用有变化时才调用；后者命中时触发快路径。代码在 `runtime/src/game_runtime/scene/`。G1 实现这两部分，G2 扩展为[画面状态](#画面状态)服务。

### 变化与稳定

每处理一帧：

1. **降采样**：把客户区缩成 `grid_width` 列（缺省 64）、行数按宽高比取整（至少 1）的格子图，每格是所覆盖像素的平均 BGR（OpenCV `INTER_AREA`；帧比格子图还小时按帧的尺寸）。不同分辨率下格子数相同，变化比例可以比较。
2. **变化比例**：与上一处理帧的格子图逐格比较，任一通道之差超过 `cell_threshold`（缺省 8，满量程 255）的格子算变化，变化比例为变化的格子占全部格子的比例。第一帧与尺寸变化后的第一帧没有可比的上一帧，变化比例记为 1。只改变换版本（窗口移动）、内容没变时不算变化。
3. **稳定时长**：本帧的采集时刻减最近一次变化比例大于 0 的帧的采集时刻，本帧有变化时为 0。
4. **稳定性**：稳定时长不短于 `stable_after`（缺省 0.25 秒）为**已稳定**；否则变化比例不低于 `transition_fraction`（缺省 0.5）为**过场**（切换画面、淡入淡出、整屏的动画）；其余为**变化中**（逐字显示、计时条走动、局部动画）。

没有新帧时结果不更新，帧不再前进由帧龄反映（[帧龄](core-protocol.md#帧龄)）。持续的局部动画（闪烁的继续标记、倒计时）让画面一直处在变化中；有时限的画面靠签名识别，不等稳定（[快路径](game-adapter.md#快路径)）。参数是插件配置，按游戏调整在标定时进行。

### 画面签名的判别

签名的声明见[画面签名](game-adapter.md#画面签名)，模板文件见[模板文件](game-adapter.md#模板文件)，来源与审核见[快路径](game-adapter.md#快路径)。没有组成项的签名尚未标定，不参与判别；ROI 与点按[声明文件](game-adapter.md#声明文件)的坐标约定换算到本帧的客户区。

**分辨率。** 模板按适配包的期望客户区分辨率 W×H 标定。本帧 w×h 的宽高比与 W∶H 相差超过 1%（\|w/h − W/H\| > 0.01·W/H）即分辨率不符：本帧不判别签名，结果为停用，尺寸每变一次记一条告警；变化与稳定照常。宽高比相符时模板按 w/W 与 h/H 缩放，ROI 与点本来就是归一化的。

**组成项。** 按像素检查、锚点、固定文字的顺序判别，每一项通过、不通过或不可判：

| 组成项 | 判别 |
| --- | --- |
| 像素检查 | 点所在像素的 R、G、B 与 `color` 之差都不超过 `tolerance` 即通过 |
| 锚点 | 模板缩放到 round(宽·w/W) × round(高·h/H)（各至少 1 像素；缩小用 `INTER_AREA`，放大用 `INTER_LINEAR`），以 OpenCV `matchTemplate` 的 `TM_CCOEFF_NORMED` 在本帧 ROI 的 BGR 像素上匹配；得分为各位置的最大值，限在 [0, 1]，不低于 `min_score` 即通过，同时给出得分最高的位置（客户区物理像素）。模板缺失、摘要不符或解不开，缩放后比 ROI 大或各像素相同，都不可判 |
| 固定文字 | 以 OCR 读出 ROI 内的各行文字，按[语言核对](game-adapter.md#语言核对)的规则与 `text` 比对，相符即通过。没有 OCR 或 OCR 出错时不可判，不当作通过 |

**签名的结果。** 任一项不通过即**不命中**，后面的项不再判别，所以前面的项都没有不通过时才调用 OCR；否则有不可判的项即**不可判**，写明是哪一项与原因；全部通过即**命中**。

**画面。** 命中的签名中只取叠加优先级（`priority`）最高的一档，按它们指向的画面给出结果：

| 结果 | 条件 |
| --- | --- |
| 画面 | 最高档的命中都指向同一个画面，且没有能改变结果的不可判签名；给出画面与这一档命中的签名 |
| 歧义 | 最高档的命中指向多于一个画面，且没有优先级更高的不可判签名 |
| 不命中 | 没有命中，也没有不可判的签名 |
| 不可判 | 不可判的签名可能改变结果：没有命中时有任何不可判；有命中时有优先级高于最高档的不可判，或与最高档同级、指向别的画面的不可判 |
| 停用 | 分辨率不符 |

只有“画面”给出画面；其余都不触发快路径，交给通用视觉智能体。优先级低于最高档的签名，无论命中与否都被叠加排除。

### 固定文字的 OCR 接口

`scene@1` 把 `ocr@1` 作为可选依赖（[清单](plugin-kernel.md#清单)），每处理一帧前探测一次，不在即本帧的固定文字项都不可判。`ocr@1` 的服务须提供：

```python
def read_lines(self, frame: RingFrame, rect: PixelRect) -> Sequence[str]: ...
```

- 识别 `frame` 在 `rect`（客户区物理像素，含左边与上边、不含右边与下边）内的文字，按阅读顺序返回各行。
- 在 `scene@1` 的工作线程里同步调用，可以阻塞；须能在多个线程里同时调用。识别不了时抛异常，该项不可判。
- 同一 ROI 的像素没变时，`scene@1` 沿用上次读出的各行，不再调用（按 ROI 与像素内容的摘要缓存最近 32 项）。
- `ocr@1` 的 `OcrService.read_lines` 实现这一接口，见 OCR 的[接口](#接口)。

### 输出

每处理一帧给出一个 `SceneState`：

| 字段 | 含义 |
| --- | --- |
| `frame_number`、`capture_ns`、`transform_version`、`width`、`height` | 所判的帧 |
| `stability` | `stable`（已稳定）、`changing`（变化中）、`transition`（过场） |
| `stable_ns` | 稳定时长，纳秒 |
| `changed_fraction` | 变化比例 |
| `verdict` | `screen`（画面）、`ambiguous`（歧义）、`none`（不命中）、`undetermined`（不可判）、`disabled`（停用） |
| `screen` | `verdict` 为 `screen` 时的画面 `id`，否则为空 |
| `matched` | 最高档中命中的签名 `id`（画面与歧义时），否则为空 |
| `signatures` | 每个参与判别的签名的结果：`id`、`screen`、`priority`、命中、不命中或不可判、说明（第一项不通过的或不可判的组成项及原因）、各锚点的得分与位置 |
| `detail` | 结果的说明：停用时的分辨率、不可判时是哪些签名 |

服务 `scene@1`（`SceneService`）：

- `latest`：最近一次的 `SceneUpdate`（帧与它的 `SceneState`），还没有时为 None。
- `subscribe(listener)`：监听者按处理的顺序收到每一帧的 `SceneUpdate`，返回取消订阅的函数，订阅方把它登记为撤销函数。监听者在事件循环里同步调用，抛错只记录，不影响其它监听者；要做重活的监听者自己排队。
- `problems`：激活时发现的、使签名不可判的问题（模板缺失、摘要不符等），同时记 ERROR 日志。

### 插件

- **清单**：普通插件 `scene`，提供 `scene@1`；依赖 `game-adapter@1` 与可选的 `ocr@1`；权限 `frames.read`。
- **配置**：`grid_width`（4–1024）、`cell_threshold`（0–254）、`stable_after`（秒，大于 0）、`transition_fraction`（大于 0、至多 1），以及 `data_dir`：本地数据目录，绝对路径，缺省按[术语](../architecture.md#术语)中的位置与 `BELLIS_GAME_RUNTIME_DATA`。
- **激活**：在工作线程里按适配包读入锚点模板，启动读帧任务，提供 `scene@1`。宿主没有给出帧源（`ctx.frames` 抛 `LookupError`）即激活失败。
- **运行**：读帧失败时记一条告警，稍后重试，恢复前不再重复记录；积压超限（`FrameBacklogError`）记 ERROR 日志，从它给出的 `resume_after` 继续；判别出错记 ERROR 日志，跳过这一帧。帧源结束即停止读帧。
- **停用**：取消读帧任务，等在途的判别做完。

## 画面状态

（GR-32）`scene@1` 在 G2 扩展为画面状态服务，是逐步控制、动作风险、模式仲裁与 planner 读取画面类型的唯一入口。

**输出**：稳定性（已稳定、变化中、过场）、画面类型、来源与置信度、命中的签名、可点击元素、帧号与变换版本。来源分三种，信任等级不同：

| 来源 | 给出者 | 信任 |
| --- | --- | --- |
| 签名 | 快路径与危险画面的画面签名 | 确定性，是唯一能放宽限制的来源 |
| 检测 | 界面元素检测模型（第二款游戏起） | 只给元素框，不定画面类型 |
| 观察 | 通用视觉智能体的观察 | 不可信数据，只能收紧 |

**观察只能收紧，不能放宽**：观察为危险画面时按危险画面处理，但不能解除签名、禁用词、静态禁区或前置条件施加的任何限制。这条规则只在这里实现一次，使用方按来源取用（[逐步控制](step-control.md#画面类型)）。

**通用画面类型**：对话、选择、计时选择、菜单、设置、存读档、商店、加载、过场、即时玩法、地图、背包、坏结局、卡住、未知；代码与声明里直接以这些名称作标识。卡住与未知由运行时给出，不对应游戏的某个画面。适配包把本游戏的画面映射到这套分类，可按游戏扩展（[画面类型映射](game-adapter.md#画面类型映射)）；风险等级与仲裁规则的缺省按通用类型写一次，适配包只能收紧；`situation.observed` 的画面类型也取自这套分类（[游戏桥](game-bridge.md#消息)）。

## 配音检测

普通插件 `voice-activity@1`（GR-08）从音频环读游戏的声音（`ctx.audio`，见[音频环的挂接与读取](core-protocol.md#音频环的读写规则)），用语音检测模型判断配音忙、闲或未知，不按音量判断，带迟滞。代码在 `runtime/src/game_runtime/voice_activity/`。G1 实现。

- **面向所有游戏**（维护者 2026-11-01，通用优先）：模型与参数是插件的缺省，不按游戏标定，适配包里没有配音检测的参数；目标是在各种游戏的背景音乐、音效与环境声下大致判出配音的忙闲，占用低，不求精准。它只影响推进的快慢，不决定对错：使用方必须有不依赖它的兜底（下一条的两个最长等待），所以漏判与多判的代价只是等得久或推进早，不是做错动作。
- 推进对白要求文字完整、配音为闲且已过最短阅读时间；配音未知时以最长等待（`voice_unknown_wait`）代替闲的判定；配音一直为忙（带人声的背景音乐、环境人声）时同样以最长等待（`voice_busy_wait`）兜底，两者都从文字完整时算起。最短阅读时间与两个最长等待是[阅读节奏](game-adapter.md#阅读节奏)参数，有通用缺省，适配包可改，由使用方读取。闲的判定只覆盖到 `processed_ns`（见[变化与状态](#变化与状态)）：使用方要的是文字完整之后的声音，就等到 `processed_ns` 不早于文字完整的那一帧的采集时刻。不采音频只作音频不可用时的降级。回放时声音与画面各自尽快处理、先后与实时不同，按采集时刻这样取用才得到与实时相同的结果。
- 型号为通用、多语言的小型 ONNX 语音检测模型，在 CPU 上单线程运行；候选是 Silero VAD，GS-06 在合成的多种背景与增益下评测它的泛化与占用，达到口径即定为型号，不按某一款游戏的结果换型号或调参。

配音忙闲同时上报给 Bellis，见[游戏桥](game-bridge.md#看点与暂缓推进)。

### 结构

核心与外壳分开，实时运行、回放与 [GS-06 的评测](#gs-06-的评测)用同一个核心：

- **核心** `VoiceActivityDetector`：按块号顺序逐块喂入（`feed`），返回状态的变化；块之间可以喂入中断（`interrupt`）。不读墙钟，不碰音频环。
- **外壳** `VoiceRunner`（在插件里）：定期读音频环，把新块逐块交给核心；发现没有音频环或块号不前进时喂入中断；发布状态、变化与喂入标记（见[确定性与回放](#确定性与回放)）。`ctx.audio` 是录制的声音时按录制喂入。

### 读取

- 每隔 `poll_interval`（缺省 20 ms）调用一次 `read_recent`：`after` 为已交给核心的最大块号，所求时长足够长，读到其后的全部块（至多音频环里的全部块，缺省约 4 秒）。启动后第一次读到的是音频环里现有的最近一段。
- 读到的块按块号顺序逐块喂入，不合并，所以一次读到几块不影响结果。处理不过来时下一次读到的块更多；落后超过音频环的容量时其间的块已被覆盖，按空缺处理。
- 读到 None（没有音频环）时喂入中断，`after` 归零。没有新块时看一眼最新一块，块号比 `after` 小即换了音频环，`after` 归零从头读。
- 读到撕裂或损坏的块时这次不读，稍后再读，恢复前只记一条告警。
- **线程**：读音频环在事件循环里：每次只拷新块（缺省格式下 10 ms 一块 3840 字节），`CoreLink` 也在事件循环里销毁音频环，读与销毁不会并发。核心（重采样与模型推理）在工作线程里运行，不阻塞事件循环，同一时刻只有一个线程调用它；被取消时等在途的工作做完再交出取消，同[取帧](#取帧)。

### 预处理

- **混音**：各声道取平均成为单声道；非有限的样本值按 0。
- **重采样**：模型要 16 kHz。音频环的采样率不同时，以有理数比的多相重采样流式地转换（缺省的 48 kHz 即 3∶1 降采样）：低通核是 Kaiser 窗（β = 8）的 sinc，截止在两边较低的奈奎斯特频率的 90%，每侧 16 个过零点（48 kHz 时每侧 54 个输入采样点，约 1.1 ms）；每个相位的权重归一化到和为 1；段的开头之前按零填充。采样率相同时不转换。
- **分帧**：16 kHz 下每 512 个采样点（32 ms）一帧。
- **采集时刻**：16 kHz 下的第 k 个采样点在输入的位置 k × 输入采样率 / 16000 上，按含这个位置的块的采集时刻加上它在块内的偏移推算（第 i 个采样点为 `capture_ns + i × 10⁹ / sample_rate`，向下取整，见[音频环](core-protocol.md#音频环)），不用墙钟。
- 同样的采样值序列，无论分成多长的块喂入，重采样与分帧得到的样本值按位相同。

### 语音检测模型

- Silero VAD v6.2 的 ONNX 模型，经 ONNX Runtime 在 CPU 上运行。模型有递归状态：每帧前面接上上一帧末尾的 64 个采样点，连同上一帧留下的状态一起送入，输出这一帧是语音的概率；新的一段从零状态开始。
- 核心只依赖 `SpeechModel` 接口（`sample_rate`、`frame_size`、`reset`、`probability`），按 GS-06 换型号不改核心。
- **线程**：算子内与算子间各 1 个线程，顺序执行。每帧的计算量很小：本机（Windows 11，混合架构的 CPU，2026-11-01）上连续推理 2000 帧，1、2、4 个线程与由 ONNX Runtime 自定时每帧分别约 0.080、0.075、0.071、0.070 ms（一帧是 32 ms 的声音），多开线程几乎不快，还要占游戏与 OCR 的核心；单线程也让同一台机器上同样的输入给出同样的概率。
- **占用的目标**：预处理与推理合计，每处理 1 秒的声音耗时不超过 30 ms（约一个核心的 3%）；GS-06 记录实测值，超出即先减少读取与拷贝，再考虑换更小的模型。
- **制品**：清单在 `runtime/src/game_runtime/voice_activity/models.py`，管理规则见[模型制品](game-adapter.md#模型制品)；配置 `data_dir` 是本地数据目录，绝对路径，缺省按[术语](../architecture.md#术语)中的位置与 `BELLIS_GAME_RUNTIME_DATA`。激活时核对大小与 SHA-256，没有或不符即激活失败并提示运行 `uv run fetch-models`；输入输出不是 Silero VAD 的接口时同样激活失败：

| 制品 | 来源 | 许可 |
| --- | --- | --- |
| `silero-vad`（`silero_vad.onnx`，8 kHz 与 16 kHz 两用） | 模型作者 Silero 在 GitHub 仓库 `snakers4/silero-vad` 里直接发布 ONNX 文件（发布页不另附文件，pip 包也打包同一个文件），钉在标签 v6.2 的 `src/silero_vad/data/silero_vad.onnx`；标签 v6.2.1 到 v6.2.3 中是同一个文件 | MIT |

### 状态与迟滞

三种状态：忙（`busy`）、闲（`idle`）、未知（`unknown`）。每帧按概率 p 分为语音帧（p ≥ `onset`）、非语音帧（p < `offset`）与其间的中间帧。

- 连续的语音帧累计到 `min_speech` 即转为忙，连续的非语音帧累计到 `min_silence` 即转为闲；中间帧打断两种累计，不改变状态，所以 `onset` 与 `offset` 之间是迟滞带。累计到某个时长指帧数乘以 32 ms 不短于它，至少 1 帧。
- 未知时同样按这两条转为忙或闲，所以断开之后至少要 `min_speech` 或 `min_silence` 的声音才有判定。
- 缺省 `onset` 0.5、`offset` 0.35，同 Silero VAD 自带的流式判定（阈值 0.5，退出阈值低 0.15）；`min_speech` 0.1 秒（4 帧）；`min_silence` 0.5 秒（16 帧），比 Silero 缺省的 100 ms 长，因为一句配音里的停顿判成闲就会在句中推进。这些都是插件的缺省，不按游戏调；GS-06 在合成样本上复核一次后固定。

### 未知

| 原因 | 何时 |
| --- | --- |
| `starting` | 启动以来还没有判定 |
| `no-audio` | 读到 None：没有音频环（没有配置音频，或实时核还没有启动、已停止） |
| `stalled` | 没有新块，且最新一块的末尾早于现在超过 `stall_timeout`（缺省 0.5 秒），还没有块时从开始等的时刻算。实时核在游戏安静时也照常写静音的块（[音频管线](realtime-core.md#音频管线)），所以这说明音频源出了问题，不是游戏安静 |
| `discontinuity` | 块带不连续标志，或采样率、声道数变了 |
| `gap` | 块号不是上一块加一：读得太慢、其间的块已被覆盖，或换了音频环 |
| `error` | 检测出错（如模型推理失败）：记录后停止检测，停在未知，停用再启用插件才恢复 |

`starting` 以外的每一项都断开当前的一段：丢掉重采样器、帧缓冲与模型状态，清掉迟滞的累计，立即转为未知；之后的块开始新的一段。新一段的第一块带不连续标志不算断开。

### 变化与状态

状态或未知的原因变了即有一条变化 `VoiceChange`，时刻都是采集时刻：

| 字段 | 含义 |
| --- | --- |
| `state` | `busy`、`idle` 或 `unknown` |
| `at_ns` | 判定时刻：忙与闲为做出判定的那一帧末尾的采集时刻；未知为引起断开的那一块的采集时刻，或中断的时刻 |
| `since_ns` | 估计的转换时刻：忙为连续语音帧中第一帧的开头，闲为连续非语音帧中第一帧的开头；未知同 `at_ns` |
| `reason` | 未知的原因，忙与闲时为空 |

当前状态 `VoiceStatus`：`state`、`reason`、`since_ns`（当前状态的转换时刻，启动以来没变过时为空）与 `processed_ns`（最近处理的一帧末尾的采集时刻，判定覆盖到这一刻；还没处理过声音时为空）。

服务 `voice-activity@1`（`VoiceActivityService`）：

- `status`：当前状态。
- `subscribe(listener)`：监听者按发生的顺序收到每一条变化，返回取消订阅的函数，订阅方把它登记为撤销函数。监听者在事件循环里同步调用，抛错只记录，不影响其它监听者。

### 确定性与回放

- 核心的输出只取决于喂入的序列：块（块号、采集时刻、采样点数、不连续标志、样本值）与格式、中断（原因与时刻），以及模型。
- 块驱动的判定（模型、迟滞、不连续与空缺）在回放中按同样的块序列复现。`no-audio` 与 `stalled` 是外壳按墙钟发现的，不在块里：回放要得到同样的变化序列，就把实时运行时喂入的中断与块按原来的顺序一起喂给核心。
- **喂入标记**：外壳把块号之外喂入核心的事按发生的顺序发布为喂入标记，每个标记带 `after`（此前喂入的最后一块的块号，还没有为 0）：

| 标记 | 何时 |
| --- | --- |
| `FeedSkip(after, next_block)` | 喂入的下一块不是 `after + 1`：启动后的第一块不是 1（实时运行开始时音频环里更早的块已被覆盖），或读得太慢、其间的块已被覆盖 |
| `FeedInterrupt(after, reason, at_ns)` | 喂入了中断：`no-audio`、`stalled` 或 `error` |
| `FeedEnd(after)` | 外壳不发布：记录标记的一方停止记录时外壳喂到的位置 |

- 服务另有 `fed_block`（已喂入、变化已发布的最后一块）与 `subscribe_feed(listener)`（按发生的顺序收到每个标记，规则同 `subscribe`）。录制时 `results` 插件把标记写进录制的 `live/voice-feed.jsonl`，停用时末尾写 `FeedEnd(fed_block)`（[M0 回放](offline-tools.md#m0-回放)）。
- **按录制喂入**：`ctx.audio` 满足 `RecordedAudio`（`next_blocks(after)` 给出录下的下一批块，`voice_marks()` 给出录下的标记）时，外壳不读墙钟、不调用 `read_recent`：按块号依次取录下的块，在每个标记记下的位置上处理它——`FeedSkip` 之前的块不喂，中断照原样喂入，到 `FeedEnd` 或 `error` 中断为止；之后的块读完不喂，读完即结束。回放出的变化与标记因此与实时逐条相同，录下的块比实时运行读到的多（录制先于插件开始）也没有关系。

### 配音检测的插件

- **清单**：普通插件 `voice-activity`，提供 `voice-activity@1`；权限 `audio.read`。不依赖 `game-adapter@1`：音频目标由宿主按适配包的窗口识别设定，`voice_unknown_wait` 由使用方读取，本插件用不到适配包的其它内容。
- **配置**：`data_dir`（见[语音检测模型](#语音检测模型)）；`onset`、`offset`（大于 0、至多 1，`offset` 不大于 `onset`）；`min_speech`、`min_silence`、`stall_timeout`（秒，大于 0、至多 60）；`poll_interval`（秒，大于 0、至多 1）。
- **激活**：在工作线程里核对并加载模型制品，启动读音频的任务，提供 `voice-activity@1`。宿主没有给出音频（`ctx.audio` 抛 `LookupError`）、模型制品没有或不符、接口不符即激活失败。
- **停用**：取消读音频的任务，等在途的推理做完。

### GS-06 的评测

离线工具 `tools/gs06-eval/`（`uv run gs06`），不进运行时，以与插件相同的核心与参数评测 [GS-06](../plan/spikes.md)。命令与选项由 `--help` 列出。

- **输入**：WAV（PCM 16、24、32 位整数或 32、64 位浮点，含 `WAVE_FORMAT_EXTENSIBLE`，单声道或立体声）；录制里的游戏声音以 `uv run recording export-audio` 导出后同样可用。
- **样本**：以合成样本为主（维护者 2026-11-01，通用优先：评测的是对各种游戏的泛化，不是对某一款游戏的拟合）。`uv run gs06 synth` 生成几把 SAPI 声音、几种语速的原创台词作纯配音；背景为音乐样（和弦与旋律）、音效样（短促的敲击与噪声）、宽带噪声，以及另一把人声按低电平作“带人声的背景音乐”的代用，组成见下文的合成。录下游戏的纯配音与纯背景不是必需的，有了可以作补充，按同样的流程评测。各段的采样率与声道数须相同。
- **真值**：从纯配音的录音算出。混成单声道，每 10 ms 一帧算均方根电平（dBFS）；高于阈值的帧为有声，阈值为第 95 百分位的电平减 30 dB、但不低于 −60 dBFS；间隔短于 0.3 秒的有声段合并，短于 0.1 秒的段丢掉。这几个参数可在命令行上改。
- **情形**：纯配音（无背景）；纯配音加每段背景，背景按每个增益（缺省 −12、−6、0、+6 dB，相对配音的电平）缩放后相加；另有每段背景单独按 0 dB 一项（没有配音，判定的忙都是多判）。背景比配音短时循环，长时截断。
- **电平**：配音的电平为真值段内的均方根电平；背景的电平为它循环或截断到配音的长度后整段的均方根电平。增益 g dB 即把背景缩放到配音的电平加 g；报告记下各段的电平与实际乘上的增益。正常混音与录制里配音与背景的相对音量按同样的定义估计。
- **口径**：纯配音与背景不高于配音电平（增益 ≤ 0 dB）的各情形设门槛，每个情形分别判定，四项都满足才算达标：漏判的段不超过真值段数的 5%、多判的时长不超过真值为闲的 10%、开始延迟 p90 不超过 0.5 秒、结束延迟 p90 不超过 1.0 秒；没法计算的项（如没有可计的延迟）算不满足。+6 dB、带人声的背景与只有背景的各项只记录，不设门槛，运行时靠最长等待兜底（[配音检测](#配音检测)）。占用见下文。达到即固定型号与参数；达不到先调迟滞参数，仍达不到再在技术基线登记候选型号。
- **判定**：把混合后的声音按音频环的样子切成 10 ms 的块，采集时刻从 0 起按采样率推算，逐块喂给核心。判定的忙段从转为忙的判定时刻（`at_ns`）到下一条变化的判定时刻；未知的时长不计入下列比例。
- **延迟**：对每个真值段 [s, e)：开始延迟为与它相交的忙段中最早的开始减 s，这个忙段在 s − 0.25 秒之前就已开始（接着上一段）时不计；结束延迟为与它相交的忙段中最晚的结束减 e，这个忙段延续到下一个真值段时不计，负值即提前判闲。各给出个数、平均、最小、中位数、p90、p95 与最大。
- **误判**：漏判为没有任何相交忙段的真值段数，以及真值为忙而判定不是忙的时长占真值忙的比例；多判为与任何真值段（向后延 1 秒）都不相交的忙段数，以及真值为闲而判定为忙的时长占真值闲的比例。每个真值段开头的 0.25 秒与结束后的 1 秒不计入两个比例，那是延迟，另计。句中判闲为在真值段之内由忙转闲的次数，这会在句中推进。两个容差可在命令行上改。
- **占用**：每个情形逐块喂入核心的墙钟耗时（重采样、分帧、推理与迟滞；不含读文件、混合与切块），评测开始前先以纯配音的前 2 秒预热模型，不计入。各情形合计的耗时除以声音的总时长即每秒声音的处理耗时，与[语音检测模型](#语音检测模型)里占用的目标（30 ms）比较；另给出最慢的情形与每帧的耗时。
- **正常混音与录制里的游戏声音**：没有逐段的真值；给出判定的忙段、忙的时长占比与电平，用来估计游戏里配音与背景的相对音量、选择增益。录制另与同一录制的剧情记录做一致性核对：每句完整的对白期间有没有判到忙，忙的起止与句的起止（按剧情记录的采集时刻）相差多少；这是粗核对，记录但不算准确率。
- **模型**：缺省用本地数据目录里核对过的候选制品；`--model` 可换成另一个同接口的模型文件，对照别的型号。
- **报告**：JSON 写到不入库的 `reports/gs06/`，命令行打印摘要；记录日期、系统、命令、模型文件与它的 SHA-256、参数与口径、各输入的文件名与时长、各段的电平；每个情形的指标、是否设门槛与各项是否满足，设门槛的情形中达标的个数与不达标的情形；占用。有每句的出处（整组评测）时，另按语音与按语速合计设门槛的各情形，给出真值段数、漏判段数与开始、结束延迟的 p90，看对不同声音与语速的泛化。
- **整组评测**：`uv run gs06 eval --suite <目录>` 按目录里的清单 `suite.toml` 评测 `gs06 synth` 写出的整组样本；也可以逐个给出文件：`--voice <纯配音>`、每段背景 `--background 名字=<WAV>`、带人声的背景 `--vocal-background 名字=<WAV>`、`--mix <正常混音>`。
- **合成**：`uv run gs06 synth <目录>` 用 Windows 自带的语音合成生成整组样本，写成 32 位浮点的 WAV 与清单；不用任何游戏音频，台词都是为评测原创的。只在 Windows 上；采样率缺省 48 kHz（`--sample-rate`，取 SAPI 支持的）。
  - **语音**：经 PowerShell 用 SAPI 5 的 COM 接口（`SAPI.SpVoice`），取 SAPI 的桌面语音与 Windows 设置里装的 OneCore 语音（登记在 `HKLM\SOFTWARE\Microsoft\Speech_OneCore\Voices`），只读这两处的登记，不改系统设置。中文的在前，至多 4 把；其后是有原创台词的其它语言（英语、日语）的，至多 2 把；`--max-voices` 再限总数。
  - **纯配音** `voice.wav`：每把语音按每种语速（SAPI 的 −10 到 10，缺省 −3、0、+4，`--rates`）读 4 句，句子在这种语言的原创台词里依次轮换；句间静音 0.8–2 秒（固定的随机种子），开头 1 秒、末尾 1.5 秒。复制成立体声。
  - **背景**，长度同纯配音，立体声：音乐样 `music.wav`（和弦与旋律）；音效样 `effects.wav`（随机时刻的敲击、铃声与风声样的噪声）；宽带噪声 `noise.wav`（粉红噪声，两个声道互不相关）；带人声的背景音乐的代用 `vocal-music.wav`：另一段音乐样，加上选中的最后一把语音（只有一把时即它）不停地读另一组原创台词，句间 0.3–0.8 秒，人声比音乐低 6 dB。
  - **正常混音** `mix.wav`：纯配音加音乐样与音效样，各按 −12 dB。
  - **清单** `suite.toml`：`voice`、`mix` 的文件名，每段背景一个 `[[backgrounds]]`（`name`、`file`，带人声的写 `vocal = true`），每句一个 `[[lines]]`（语音的名字 `voice`、语言 `culture`、语速 `rate`、这句在纯配音里的起止 `start`、`end`（秒）与 `text`）。文件名相对清单所在的目录。

## 界面元素检测

本地界面元素检测模型（OmniParser 一类，GR-24），在本机 CPU 或 GPU 上运行，给出可点击元素的框，与 OCR 识别框一起作为吸附目标。

- 型号与许可在首个实现前登记审核，由 GS-09 评估；模型文件作为制品管理。
- 不用任何游戏截图训练或微调。
