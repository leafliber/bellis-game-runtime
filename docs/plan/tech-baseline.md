# 技术基线与路线审核

本文件是 Game Runtime 技术选型的唯一登记处，规则与 [Bellis 技术基线](https://github.com/leafliber/bellis/blob/main/docs/plan/tech-baseline.md)相同：

- 只有“已批准”的决策和路线可以写进架构、模块文档与任务卡，作为实现依据。
- 需要新选型时，先在“待审核路线”登记候选、推荐与依据，由维护者审核；审核前不得在代码或文档中把候选写成定论。
- 批准、否决或改选都直接修改本文件对应的行，不另写评审记录。批准后的路线保留原编号，移到“已批准的路线”，并把设计细节写进“详见”所指的文档。
- 每行只写选了什么、为什么；怎么做写在所指的模块文档，不在这里重复。

本仓库的编号用 GD-xx（决策）与 GR-xx（路线），探针用 GS-xx，合规确认用 C-x（见[合规](../compliance.md#合规确认)），以免与 Bellis 的 D-xx、R-xx、S-xx 混淆；引用 Bellis 的条目时写明“Bellis”。

## 继承的 Bellis 决策

以下条目在 Bellis 批准，同样约束本仓库，内容以 Bellis 技术基线为准，这里只列出与本仓库相关的部分。

| Bellis 编号 | 对本仓库的约束 |
| --- | --- |
| D-01、D-02、D-03、D-05 | 最终目标是在已适配游戏中以 VLA 方式自主游玩原神这类游戏；零样本通关未适配游戏、直播中在线训练并上线不是目标；VLA 是主线，与 Bellis 的 P0–P3 并行研究 |
| D-04、D-27 | 采集、感知、VLA 策略、输入代理和训练都在本仓库；逐帧控制不经过 Bellis；与 Bellis 之间只传语言子目标与结构化字段，输入许可短周期续约、过期即释放全部输入，潜向量不出本仓库 |
| D-06、D-07 | 首个公开里程碑是《魔法少女的魔女审判》；无计时选项由 AI 决定是否开观众投票，有计时选项由 AI 自选，超时按 Game Runtime 的默认策略处理 |
| D-08 | 游戏文本用 OCR 与 VLM 获取，两者是独立插件，可分别开关 |
| D-11 | 生产平台只有 Windows 11 x64；三平台 CI 运行完整检查，CI 通过不构成验收。本仓库不用托管 CI，完整检查在本机运行（GR-29） |
| D-12、R-05 | 本机通道用 Windows 命名管道 / POSIX UDS，应用层双向 HMAC 认证，认证前不传数据 |
| D-22 | 先单机；真机测出 GPU 争用后再决定是否加推理机 |
| D-31、D-34 | 执行许可令牌只增不减，设备只接受等于当前令牌且未过期的指令；游戏输入许可初值约 500ms，每 250ms 内续约 |
| R-06 | 子进程停止顺序为 RPC 关闭 → 关 stdin → 超时终止；Windows 上用 Job Object 管住孙进程 |
| R-23 | 不由 Bellis 拉起的进程从 SecretStore 读取本次会话的连接信息 |
| [合规](https://github.com/leafliber/bellis/blob/main/docs/compliance.md#游戏) | 《魔女审判》的文本只用屏幕 OCR 与 VLM 获取，不解析游戏数据；游戏画面不进入任何训练集 |

## 已批准的决策

| 编号 | 决策 | 内容 | 批准日期 |
| --- | --- | --- | --- |
| GD-01 | 实现架构 | 两个进程：Python 主进程负责感知、剧情理解、规划、策略与游戏桥的语义部分，工具链沿用 Bellis R-24（Python 3.12，uv 管理解释器、虚拟环境与依赖，锁文件入库，ruff、pyright、pytest）；Rust 实时核负责采集、共享内存帧环和唯一的输入代理（许可与持键账目、白名单、前台核验、释放、低层钩子），按游戏需要提权。两者之间以动作块为唯一的动作形式。依据：按原神场景倒推，只有实时核需要提权，定时与钩子不受 GIL 与 GC 影响，主进程故障时由实时核释放输入，策略部分以后可以迁到推理机；剧情游戏只用其中一部分能力。详见[总体架构](../architecture.md) | 2026-10-27 |
| GD-02 | 管理模型 | 按 Bellis 的规划对齐，需要时可以扩展：授权从上往下给，数据从下往上报；实时核相当于游戏侧的安全核，是唯一的输入写入者，任何时刻只有一个控制产出者；扩展只产出数据和候选，没有权威；游戏内容是不可信数据；长期记忆只经 Bellis 写入；游戏与 profile 由操作员选择；主进程沿用 Bellis 插件内核的概念与分级（关键平面、普通插件）；非提权一方创建全部进程间对象（可达性由 GS-03 验证）；全部本机通道沿用 Bellis R-05。详见[总体架构](../architecture.md#权威) | 2026-10-27 |
| GD-03 | 游戏桥契约来源 | 以 Bellis `packages/protocol`（TypeBox，Bellis D-21）为唯一的源；本仓库锁定某个 Bellis 提交的生成物（JSON Schema 与 Pydantic 模型），并有检查核对锁定副本未被改动；改动先在 Bellis 合入，本仓库再更新。详见[游戏桥](../modules/game-bridge.md#契约) | 2026-10-27 |
| GD-04 | 控制的组织 | 控制模式与策略后端分开：控制模式只管时序（逐步模式：看一帧、做一个动作、再看一帧；连续模式：按固定频率下发动作块），策略后端决定动作。所有后端按同一份策略后端契约接入（GR-33），输出同一套统一动作空间（含调用技能，GR-34），经同一个实时核核验。通用视觉智能体是底座，游戏适配包的快路径可选：每款游戏只须提供窗口识别、动作白名单、合规声明、期望分辨率、语言版本与画面类型映射（GR-16、GR-32）即可以逐步模式运行。逐步模式下由一个逐步控制器作为唯一的控制产出者，每步在快路径与通用智能体之间选择；切到连续模式的后端（如 VLA）属于更换控制产出者，先释放输入。降低的是适配成本，零样本通关仍不是目标（Bellis D-02）。详见[总体架构](../architecture.md#控制的组织) | 2026-10-27，修订 2026-10-30 |
| GD-05 | 阶段划分 | G0 工程骨架与实时核闭环 → G1 只读感知 → G2 受监督的自动游玩（独立运行）→ G3 游戏桥联调（与 Bellis P3 同步）→ 随 Bellis T1 公开试播，之后进入原神阶段；VLA 研究离线并行（Bellis D-05）。依据：最危险的部分（输入释放、跨进程失效）先在假输入后端上做实，再接真实输入；只读感知不需要输入许可，可在维护者手动游玩时积累样本、验证 OCR 与画面识别；G3 依赖 Bellis P3 冻结契约，不阻塞 G0–G2。详见[路线图](roadmap.md) | 2026-10-28 |

| GR-14 | 剧情理解 | 放在 Game Runtime 的规划与理解层，Bellis 决策模型只做选择与表达；主进程两个普通插件：`narrative@1` 记录剧情（存本机，完整日志不出本机），`planner@1` 维护摘要与笔记，产出局面摘要、决策候选与当前目标，不做选择。详见[剧情记录与规划](../modules/narrative-planner.md)；Bellis 侧见提案 P-02、P-03 | 2026-10-28 |
| GR-15 | 坏结局策略 | 不使用攻略。坏结局经快路径或智能体识别后上报并停止推进，等 Bellis 给出继续的目标才用游戏自带的重来入口；保留失败记录，失败过的选项在候选中标为已试过；连续失败达上限即上报卡住。详见[坏结局与重来](../modules/narrative-planner.md#坏结局与重来)；Bellis 侧见提案 P-04 | 2026-10-28 |
| GR-16 | 游戏语言版本 | 《魔女审判》用简体中文版，整局固定；启动时核对语言，不符即不进入自动游玩。详见[《魔女审判》适配](../games/witch-trial.md#版本与语言) | 2026-10-28 |
| GR-17 | planner 的调用时机 | 记录剧情不调用模型；摘要与笔记批量更新（间隔可配置，缺省值见调用时机），画面事件立即更新；审判发言、决策点、坏结局与新目标立即调用；单个在途调用。依据：按每句 4–8 秒估算，每句调用每小时要调几百次，大多只是给摘要追加一句。详见[调用时机](../modules/narrative-planner.md#调用时机) | 2026-10-28，修订 2026-10-30 |
| GR-18 | 按用途选模型 | 同一个薄客户端，模型按用途（智能体、推理、摘要、关键帧、标定）分别配置；允许清单按厂商与请求 `model` 字段的完整值（型号 ID 或接入点 ID）核对，与用途无关；缺省全部 `glm-5-3-flash`，各用途的型号由 GS-07 对照后定。依据：`glm-5-3-flash` 的思考不能关闭（Bellis R-17），放在每步一次的智能体上时延代价最大；摘要不需要强推理。详见[模型接入](../modules/models.md#按用途配置) | 2026-10-28，修订 2026-10-30 |
| GR-19 | 观察随动作输出 | 不单独调用 VLM 描述画面：通用视觉智能体每次输出观察与动作，快路径画面的描述由结构化结果拼成，观察写入剧情记录；不为与 OCR 交叉核对单独调用 VLM；关键帧调用的边界见 GR-25。依据：少一类调用，发往云端的游戏画面也更少；观察与动作出自同一次推理，不会互相矛盾。详见[逐步控制](../modules/step-control.md#通用视觉智能体) | 2026-10-28，修订 2026-10-30 |
| GR-20 | 与 Bellis 的解说节奏 | 两边都由确定性代码处理，不额外调用 LLM：局面带看点标记与配音忙闲；Bellis 以 `pacing.hold` 与 `pacing.release` 暂停推进类与导航类动作，本地有最长暂缓时间。依据：避免决策模型每句都被触发，也避免下一句配音盖住解说；解说播完的时刻只有发声仲裁知道。详见[游戏桥](../modules/game-bridge.md#看点与暂缓推进)；Bellis 侧见提案 P-06、P-07 | 2026-10-28 |
| GR-21 | 动作风险等级与禁区 | 动作分禁止、不可逆（只能经决策点）、普通三级，缺省按通用画面类型写一次，游戏适配包按本游戏的画面映射并只能收紧（GR-32）；四道独立防线：画面类型限制（只认签名判出的画面类型）、目标文字检查、实时核的静态禁区、窗口与操作员前置条件；统一动作空间没有输入文字的动作。依据：白名单只管键位与区域，不懂语义；提示词不是强制手段，游戏画面本身是不可信数据；让实时核识别画面违背其保持最小的原则。详见[动作风险](../modules/step-control.md#动作风险)；Bellis 侧见提案 P-08 | 2026-10-28，修订 2026-10-30 |
